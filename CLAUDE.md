# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build
- `npm run preview` — preview a production build locally

- `npm test` — la batería de pruebas (`node --test`, sin dependencias: el ejecutor viene con Node). No hay ESLint.

**Las pruebas solo alcanzan `src/logica.js`, `src/colaPendientes.js` y `src/cachePreguntas.js`**, no `App.jsx`: un `.jsx` no se puede importar desde Node sin montar un transpilador. De ahí la regla: **si una función es pura — datos entran, datos salen, sin React ni Supabase ni navegador — va a `src/logica.js` y se prueba; si no, se queda en `App.jsx`.** Lo que dependa del entorno se recibe por argumento (`hoy` en `calcularSM2`, `ahora` en `reconstruirTirada`, `azar` en `ordenarPorPrioridad`) justamente para poder fijarlo en una prueba. Antes de esto, cada comprobación era una copia del código en un borrador que se tiraba al terminar: servía para pensar, no para enterarse de si un cambio de mañana rompe lo de hoy. La primera pasada ya encontró un fallo real: `esExamen` usaba `/^pir\b/i` y `\b` se apoya en `[A-Za-z0-9_]`, así que una tilde cuenta como separador y "Pirámide de Maslow" pasaba por edición de examen; ahora es `/^pir(?:[\s\d]|$)/i`.

## Architecture

This is a small single-page React app ("AUTOPIR", formerly "Ruta PIR"; repo/package name academia-pir), built with Vite, backed by Supabase.

- Entry chain: `index.html` → `src/main.jsx` → `src/App.jsx`. `src/App.jsx` is the entire application (~2000 lines): all components, view logic, and Supabase calls live in this one file, organized as several feature components rendered by a top-level `AcademiaPIR` component based on a `section` state variable (tab navigation).
- Sections/tabs (`section` state, set via the nav in `AcademiaPIR`; only 4 tabs remain, in this order): `simulacros` (self-test quizzes, labeled "Autoevaluaciones" — see below), `duelo` (1v1 duel/battle mode), `flashcards` (spaced-repetition flashcards, Anki-style, front/back cards seeded from an imported Anki deck — see `flashcards`/`flashcards_progreso` below), `perfil` (last tab: fail history, favorites — kept deliberately light; the daily wheel/"ruleta" used to live here but was relocated into the header, see phase 2 below). There is no `temario` tab — `TEMARIO` (static data in `src/temario.js`) is still imported and used internally to ground AI question generation (`GenerarPreguntasIA`), just not shown as a readable tab. There used to be a `curiosidades` tab (AI-generated trivia, via `api/generar-curiosidades.js`); it was replaced outright by `flashcards` per user request — the `curiosidades`/`curiosidades_vistas` tables and `supabase-curiosidades.sql` are dead but left in Supabase/the repo as history, nothing in `App.jsx` references them anymore.
- `banco` (question bank — "Reales" curated real-exam questions + a "Pendientes" tab of real questions not yet attempted, see the per-question progress bullet below; no course/subject filter, just a free-text search box that filters the current tab's questions by substring match against the question/options/explanation/tema) and `ranking` (leaderboard + streaks) are **not** nav tabs — like `Logros` (level/badge grid + streak & accuracy stats), they live behind small icon buttons in the header (`Header`'s `mostrarBanco`/`mostrarRanking` state, next to the pre-existing `mostrarLogros`), positioned award-icon (Logros) → trophy-icon (Ranking) → list-icon (Banco) → gear (Ajustes) → logout. Unlike `Logros`'s small anchored dropdown, clicking the Banco or Ranking icon opens a full-screen overlay (`styles.pantallaCompleta`, `position: fixed; inset: 0`, its own close/`X` button up top) rendering the exact same `<BancoPreguntas>`/`<Ranking>` components and props that used to live in the tabbed `<main>` — the components themselves are unchanged, only their entry point moved from a nav tab to a header-triggered overlay. `Header` now needs the question-bank CRUD callbacks and `rachas` passed down from the root alongside its original `user`/`onLogout`/`miRacha`/`onAjustes` props.
- **Per-question progress tracking, and the "Inventadas por IA" tab's repurposing into "Pendientes":** per user request ("para que tenga un control de que he realizado todas"), a new `preguntas_progreso` table (`supabase-preguntas-progreso.sql`, same `name`+`user_id`+RLS shape as `fallos`/`favoritos`, one row per user per question: `veces` = total times answered, `acertada` = whether any attempt was ever correct) is written to from a new root handler, `registrarProgresoPregunta(pregunta, correcta)` (upserts by `name`+`pregunta_id`, incrementing `veces` and OR-ing `acertada`), wired into both `Simulacros` (`onRespuestaPregunta`, called in `elegir` alongside `onFallo`/`onProgresoDiario`, same `ronda === 1` first-attempt-only gate so repeat-round re-answers of previously-failed questions don't double-count) and `Duelo` (`onRespuestaPregunta`, called in `responder` alongside `onProgresoDiario`) — so a question's count reflects attempts from either mode. `BancoPreguntas` reads this via a new `preguntasProgreso` prop (root → `Header` → `BancoPreguntas`) and: (1) shows a `ProgresoPreguntaBadge` (an `Eye` icon + the raw `veces` count, gray at 0/tinta once attempted/`CORRECTO`-green once ever correct, with a title tooltip spelling out the count) on every `PreguntaCard`, top-right next to the existing favorito star, so scrolling the list shows at a glance which questions are done; (2) the `SectionTitle` subtitle shows an aggregate `hechasReales/totalReales` count of real questions ever answered correctly (dynamic, not a hardcoded "2102"). The second tab — previously "Inventadas por IA" (`GenerarPreguntasIA` embedded inline, plus any already-saved AI-generated questions) — was replaced outright with "Pendientes ({count})" (`Eye` icon), listing real questions with no progress row or `veces === 0` (attempted-but-never-correct questions are deliberately excluded from both "pendientes" and the "hechas" count — they sit in "Reales" only, neither bucket, until answered correctly at least once); `GenerarPreguntasIA` itself is left defined but unreferenced (Rollup tree-shakes it out of the build), same "dead code left behind, not deleted" precedent as `curiosidades` — any already-saved `inventada` questions are no longer reachable from this screen as a result, which hasn't been raised as a problem but is worth knowing if it ever comes up.
- `PreguntaCard` (the expandable question row inside `BancoPreguntas`) no longer reveals the correct option (and the explanation, which usually gives it away) as soon as a question is expanded — a local `mostrarCorrecta` state (reset to `false` every time the card is expanded/collapsed via `toggleOpen`) gates the correct-answer highlight/checkmark and the explanation text behind a "Ver respuesta correcta" button rendered under the options list; pressing it reveals both instantly. This only applies to `PreguntaCard` — the equivalent review UIs in `Simulacros`' post-quiz screen and `MiPerfil`'s fail history still reveal the correct answer immediately, since those are reviewing an already-answered question rather than browsing the raw bank.
- `Simulacros` ("Autoevaluaciones"): the course/subject picker is labeled "Exámenes" and only lists `curso` values that look like an exam edition (matched via the module-level `esExamen(curso)` helper, a `/^pir\b/i` regex — e.g. "PIR 18", "PIR 20", "PIR 21"…"PIR 25"); the near-empty leftover subject-labeled `curso` values (e.g. "Psicopatología") are filtered out of this specific dropdown, though "Todos" still aggregates everything in the current `incluirInventadas`-scoped pool as before. The dropdown's exam options are sorted newest-first by the number in the label (e.g. PIR 26, 25, 24…), not by insertion/appearance order — extracted with a plain `/\d+/` match on the `curso` string. "Modo relámpago" was redesigned from its original fixed 5-question/60-second countdown into an unlimited streak mode: `startRelampago` shuffles every real (non-`inventada`) question across all exam-labeled cursos (`esExamen`) into the pool, questions are answered one at a time (elapsed time just ticks up for display, no time limit), and the round ends the instant an answer is wrong (`"Racha terminada"`) or the moment the whole shuffled pool has been answered correctly (`"¡Racha perfecta!"`) — there's no repeat-of-failures round like the regular mode. Each new relámpago run reshuffles from scratch (no memory of what was seen in past runs, so repeats before exhausting the pool are expected and intended). Only modo relámpago's result is submitted anywhere: `onStreakAnswer` (which drives `rachas.racha_actual`/`racha_record`, shown as the "Autoevaluaciones" columns on the Ranking tab) and `onFinish`/`submitScore` (insert into the `ranking` table — currently otherwise unused for display) are now gated to `relampago === true`; regular course-based autoevaluaciones no longer touch either, to keep that ranking driven by one well-defined game mode. `onProgresoDiario` (weekly league + daily-wheel eligibility) and `onFallo` (fail history in Perfil) are unaffected and still fire for both modes — including relámpago's own failed question, which still lands in Perfil's fail history like any other. A small persistent `rachaViva` counter (reset to 0 in `startRelampago`, incremented on every correct answer while `relampago`) sits top-right of the run header next to the timer, as a `Flame` icon + number; the flame renders dim/grey ("apagada") while `rachaViva <= recordPrevio` and switches to a lit, glowing orange state the moment the live streak exceeds that prior personal record. `recordPrevio` is **frozen at the start of the run** (a `useState` set in `startRelampago` from `miRacha.racha_record`), not read live from the prop — reading it live meant the flame never lit at all, since `registrarAcierto` raises `racha_record` to `max(récord, racha actual)` on every correct answer, so by the instant `rachaViva` passed the old record the record had already climbed to match it and `rachaViva > recordPrevio` was never true. The post-quiz "Toca una pregunta para repasarla" squares (`styles.cuadroPregunta`) were previously always rendered in the red/`ACENTO` palette regardless of outcome, which per user feedback looked like every question had been failed; they're now colored from `resultados[q.id].correct` (green/`CORRECTO` vs red/`ACENTO`) — in the regular (non-relámpago) mode this renders every square green once the round finishes, since a question only leaves the repeat-of-failures loop once answered correctly, so by the time `state === "done"` every entry in `resultados` is `correct: true` and the grid correctly reflects "you got everything right in the end"; in modo relámpago, which has no repeat round, this instead shows a true mix — green for the questions answered correctly and red for the single wrong answer that ended the streak.
- The `curso` column on `preguntas` is a free-text field, not a fixed taxonomy — for a chunk of imported real questions it actually holds an exam/simulacro label (e.g. "Simulacro 01 (AMIR)") rather than a subject name; those get renamed to their real "PIR YY" edition label via one-off `update` statements in `supabase-*.sql` files as the user requests each renaming (see `supabase-rename-simulacros.sql` for the pattern: a regex anchored on the simulacro number to avoid collisions like "1" matching "10"). Besides renamed simulacros, whole past exams have also been transcribed from PDF and `insert`ed directly with `curso` set to their edition label: `supabase-pir20-preguntas.sql` (198 questions, curso="PIR 20", from an APIR "Simulacro 5" practice-exam PDF; 12 annulled questions from the source were skipped; includes real `explicacion`/`tema` per question) and `supabase-pir18-preguntas.sql` (235 questions, curso="PIR 18", from the official 2018 PIR exam PDF cross-checked against the Ministerio de Sanidad's official answer key; no explanations exist for this source, so `tema` is a placeholder "Pregunta N" and `explicacion` is null), `supabase-pir16-preguntas.sql` (228 questions, curso="PIR 16", same official-exam-PDF-plus-answer-key pattern as PIR 18 — 7 annulled questions, identified by a blank correct-answer cell on the Ministerio's own answer page, were skipped: 23, 25, 27, 46, 69, 74, 102), `supabase-pir15-preguntas.sql` (226 questions, curso="PIR 15", same pattern — 9 annulled questions skipped: 24, 46, 84, 91, 100, 114, 125, 153, 214), and `supabase-pir19-preguntas.sql` (180 questions, curso="PIR 19" — the official exam actually sat in January 2020 under the Ministerio's own cover title "PRUEBAS SELECTIVAS 2019", 175 questions + 10 reserve = 185 numbered, 5 annulled skipped: 35, 69, 114, 134, 185; not to be confused with the already-existing curso="PIR 20", which per above is actually an unrelated APIR practice simulacro, not this official exam — before transcribing this one the user was walked through a content-based check, grepping this repo's other transcribed exam files and searching the live question bank for a distinctive phrase from this PDF, to confirm it wasn't already sitting in the database under a different label like one of the renamed "PIR 21"-"PIR 25" simulacros). All five were run by the user directly in the Supabase SQL editor. `supabase-pir16-preguntas.sql`, `supabase-pir15-preguntas.sql` and `supabase-pir19-preguntas.sql` were each generated (not hand-typed) by a throwaway Node script in the session's scratchpad that built a JS array of `{n, p, o, c}` from the transcribed PDF pages, validated every row before emitting SQL (exactly 4 options, `correcta` in 0-3, no duplicate/missing/annulled question numbers, every `pregunta` ending in `:` or `?`, and — directly per user request after the earlier `. NN`-suffix cleanup — every field checked against the same trailing "period + stray number" regex used in `supabase-detectar-basura-preguntas.sql` so that artifact couldn't be reintroduced), and only wrote the `.sql` file once all checks passed. `supabase-detectar-basura-preguntas.sql`/`supabase-detectar-finales-raros.sql` only look at the END of `pregunta`/`opciones`/`explicacion` text; a distinct artifact — leftover PDF-layout fragments pasted MID-sentence (e.g. "...de tener Pá una discapacidad..." in a PIR 25/"Simulacro" question, an unrelated short capitalized token stuck in the middle) and words merged with no space from a lost line-break (e.g. "sentimientosnegativos") — needed a separate diagnostic, `supabase-detectar-fragmentos-preguntas.sql`: one regex flags a short (1-3 letter) capitalized token surrounded by lowercase words (real domain acronyms like DSM/CIE/PIR/EMDR are always fully uppercase and don't match), another flags any 20+-letter unbroken run of letters as a candidate merged-word. `supabase-pistas-respuestas.sql` es otro diagnóstico de solo lectura, pero de otra familia: no busca erratas sino **si la forma de una opción delata que es la correcta** (paréntesis, palabras absolutas, ser la más larga o la más corta), devolviendo una tabla de cuatro filas en vez de preguntas. Lo que mide es observado contra esperado, y solo cuenta las preguntas donde la pista **discrimina** — la llevan entre 1 y 3 opciones —, porque si la llevan las cuatro no dice nada; ese detalle es lo que separa un resultado de una ilusión. **Ya se ha ejecutado sobre el banco entero** (el usuario lo corrió en Supabase y pegó las cuatro filas), así que estos números son los definitivos de las 2102, no de una muestra: el **paréntesis sale plano** (224 preguntas, 73 aciertos frente a 74,0 esperados, z ≈ −0,1) — y lo instructivo es que en la submuestra de 1067 marcaba 1,10 veces lo esperado y al doblar los datos se desplomó a 0,99, que es exactamente lo que hace el ruido; **la longitud es señal firme y en el mismo sentido en los cinco exámenes por separado**: la más larga acierta el **29,8 %** y la más corta el **20,9 %** contra el 25 % del azar (z +5,1 y −4,3), casi nueve puntos de hueco entre una y otra; y **las palabras absolutas** (siempre, nunca, todos, ninguno, exclusivamente, únicamente, solamente) aciertan **0,63 veces lo esperado** (16 frente a 25,3, z ≈ −2,2), un efecto que **solo se vio al pasar de 1067 a 2102** y que se reforzó al crecer la muestra (0,74 → 0,63), al revés que el paréntesis. La posición de la correcta es plana (a 25,3 %, b 25,0 %, c 25,9 %, d 23,8 %): no hay "ante la duda, la C". Salieron vacías también las cifras, el punto y coma, repetir palabras del enunciado y las palabras matizadas (puede, suele, generalmente). **Segunda vuelta (`supabase-pistas-respuestas-2.sql`), que es donde aparece lo bueno:** explorando 26 pistas sobre los 1067 con replicación en dos mitades (PIR 15+16+18 contra PIR 19+20), la señal más fuerte con diferencia no es la longitud sino **llevar " o "** — una disyunción, "ira o culpa", "ideas o palabras", "estímulo ambiguo o poco estructurado" —: **1,62 veces lo esperado** (72 aciertos sobre 44,3, z ≈ +5,0), por encima de 1 en **los cinco exámenes por separado** (1,28 / 1,73 / 1,91 / 1,37 / 1,68) y en las dos mitades (1,70 y 1,50). **No es la longitud disfrazada**, y esa comprobación es el núcleo del análisis: las opciones con " o " miden de media 101 caracteres contra 50, así que el efecto podía ser un artefacto — pero al descartar las preguntas donde la opción con " o " era además la más larga **sube** a 1,78 (z ≈ +3,4); y al revés, la longitud **se encoge** de 1,16 a 1,10 (z +2,99 → +1,81) cuando se quitan las preguntas que contienen algún " o ". O sea que parte de lo que parecía "la más larga acierta más" era en realidad esto. El control que lo convierte en hallazgo y no en correlación: **" y " no hace nada** (1,06, y 0,89 bajo el mismo control), así que no es "las opciones compuestas aciertan más", es específicamente **ofrecer una alternativa**, que es como se redacta un enunciado verdadero cuando tiene que ser clínicamente exacto. Bajo ese mismo control de longitud se caen la coma (1,19 → 1,14), las palabras matizadas (1,24 → 0,94) y otra vez el paréntesis (1,11 → 0,83); aguantan la dirección la negación "no" (0,79 → 0,74) y las absolutas (0,74 → 0,69). La consulta se validó igual que la primera, contra un Postgres 16 local cargado con esos 1067, fila a fila contra el análisis en Python. **Confirmado después sobre las 2102** (el usuario ejecutó la consulta y pegó las cinco filas), que es la versión que vale: **" o " acierta 1,52 veces lo esperado** (151 sobre 99,3 en 301 preguntas, z ≈ +6,3) y **1,44 descartando los casos en que además era la más larga** (55 sobre 38,3, z ≈ +3,2), así que el control de longitud aguanta con el banco entero. La longitud, ya limpia de " o ", queda en **1,13** (503 sobre 447 en 1788, z ≈ +3,1): real, pero **un tercio del efecto del " o "**. Matiz honesto que conviene no borrar: el control " y " no sale perfectamente plano con todos los datos, sino **1,08** (z ≈ +1,8) — sigue siendo un sexto del efecto de la disyunción y es compatible con un residuo de longitud, pero no es el cero limpio que daba con 1067. La negación "no" se queda en **0,86** (z ≈ −1,9), demasiado flojo para fiarse. **Lo que vale en la práctica, que es el número que hay que dar y no la z**: aplicando a la vez las cuatro pistas con una regla fijada de antemano (+2 si lleva " o ", −2 si lleva un absoluto, +1 la más larga, −1 la más corta) se acierta el **30,1 %** de las preguntas en vez del 25 % del azar, y aguanta en las dos mitades por separado (30,6 % y 29,1 %). Son **cinco puntos sobre adivinar**: una pregunta más de cada veinte que vayan totalmente a ciegas. Sirve para romper un empate, no para aprobar, y el documento lo dice así a propósito. **Tercera vuelta (`supabase-pistas-respuestas-3.sql`): la señal de DESCARTE.** Hasta aquí todo eran pistas de acierto; la petición fue buscar lo contrario. La que aparece, y replica en las dos mitades, es **"suelta y corta"**: la opción que (a) comparte menos palabras con las otras tres — Jaccard mínimo sobre palabras de 4+ letras — y (b) además mide menos que la media de su pregunta. Acierta **0,65 veces lo esperado** (27 sobre 41,0 en 164 preguntas, z ≈ −2,5), y apretando el umbral a 0,8× baja a **0,59** (16 sobre 27,0, z ≈ −2,4); 0,67/0,62 y 0,56/0,64 en las dos mitades. **Es una interacción, no la suma de dos cosas**, y ese es el punto: ser corta *sin* estar suelta da solo 0,88 (297 sobre 336,8 en 864), y estar suelta *sin* ser corta da 1,03 — o sea nada. Hace falta que se den las dos. La lectura: es el distractor de relleno, el que se escribió sin pensar y se queda descolgado del vocabulario de los otros tres. Por el lado del acierto nada bate limpiamente al " o " pelado: combinarlo con que no sea corta lo deja en 1,66 (59 sobre 35,5) con mejor replicación (1,68/1,64) pero sobre menos preguntas, así que no se vende como mejora. **Lo que NO funcionó, por no repetirlo:** el par de opciones más parecidas entre sí (1,02, el clásico "la correcta está en la pareja" aquí no existe), la opción aislada a secas, el eco literal del enunciado, los nombres propios que no salen en el enunciado, "ninguna/todas las anteriores", y los absolutos por separado (siempre, nunca, todos…), que solo dan señal agrupados. La consulta se validó otra vez contra un Postgres 16 local — importa aquí más que en las anteriores porque calcula solapamiento de palabras entre opciones con un self-join, y reproduce el análisis de Python fila a fila (164 contra 165 en una, por cómo trata los acentos). **Confirmado sobre las 2102**, que es la versión que vale: el descarte queda en **0,71** (62 sobre 86,8 en 347 preguntas, z ≈ −3,1) y **0,66** con el umbral de 0,8× (36 sobre 54,5, z ≈ −2,9) — se encoge respecto al 0,65/0,59 de la mitad, que es la regresión a la media esperable cuando un efecto se estima en pocos datos y se comprueba en todos. **La interacción aguanta**: corta pero acompañada 0,90, corta Y suelta 0,71, o sea que estar suelta aporta −0,18 por su cuenta. Y por el lado del acierto **sí hay mejora y esta vez sí se sostiene**: `" o "` **y que no sea más corta que la media** da **1,61** (119 sobre 73,8 en 237, z ≈ +6,3) y apenas se movió al doblar los datos (1,66 → 1,61), mientras que el `" o "` pelado cayó de 1,63 a 1,52; esa es ahora la mejor pista del análisis. **El matiz que impide venderlo de más**: eligiendo los pesos de una regla combinada **solo con la mitad A** y midiéndola en la **mitad B, nunca vista**, se acierta el **29,3 %** frente al 25 % del azar — y la búsqueda de pesos deja en **cero** tanto el descarte como "la más corta", porque son redundantes entre sí y con el resto: la opción que marcan casi nunca iba a ganar el ranking de todas formas. Es decir, **el descarte es un hecho real pero no suma a la regla de elegir**; donde sirve es al revés, cuando ya has reducido a dos o tres candidatas y hay que tachar una. **Y aquí se cierra la línea: NO existe una regla de precisión alta, y está comprobado, no supuesto.** Ante la pregunta de si habría algo por encima del 80 %, se minaron **2166 reglas** (conjunciones de hasta 3 rasgos sobre 16 features por opción: " o ", " y ", coma, paréntesis, cifra, absoluto, matizado, negación, más larga/corta, muy larga/corta, suelta, central, eco del enunciado, nombre propio), quedándose solo con las que **señalan una única opción** en 30+ preguntas, ajustando en la mitad A y midiendo en la B. La mejor (`" o "` + sin `" y "` + la más larga) da **55,3 % en A y 40,0 % en B**; las doce mejores pierden entre **7 y 19 puntos** al pasar a datos no vistos. Esa caída sistemática es la firma del sobreajuste, y es la respuesta: con el efecto real más grande en 1,6 veces lo esperado sobre una base del 25-33 %, no hay aritmética que llegue al 80 %. **El techo honesto de todo este análisis es ~29-30 %.** **Sobre los enunciados negativos ("señale la FALSA", "NO es", "EXCEPTO"): la conclusión es deductiva, no medida, y hubo que corregirla.** Primero se dijo que la pista de descarte "se invierte" apoyándose en que la opción más suelta acertaba el 40 % en negativos contra el 20,9 % en positivos (n=30). **Esa afirmación no se sostiene**: con la definición que de verdad se usa — suelta **y** corta — el mismo corte da 0,44 en negativos (n=9), o sea el signo contrario. Con 68 preguntas negativas de 1067 (**6 %**) quedan 9 o 10 casos utilizables por pista, y ahí no hay nada que medir. Lo que sí es sólido llegó de una objeción del usuario, y es más fuerte que el dato: **las tres pistas no predicen cuál es la CORRECTA, predicen cuál es VERDADERA.** El " o " marca la redacción exacta (verdadera); el absoluto y el relleno suelto-y-corto marcan afirmaciones falsas. En una pregunta normal verdadera = correcta, pero **cuando piden la falsa esa equivalencia se rompe y las tres deben invertirse en bloque**: el " o " pasa a descarte, y el absoluto y el relleno pasan a candidatos. El consejo anterior era incoherente — invertía una pista y dejaba las otras dos como estaban. Direccionalmente el dato acompaña en el absoluto (0,59 en positivos → 1,33 en negativos) y en el " o " (1,70 → 1,20), pero con n=9 eso es anécdota: **lo que sostiene la inversión es el mecanismo, no la muestra**, y así hay que escribirlo. Dos cautelas apuntadas: la z de las filas de recuento usa la p media por pregunta, lo que **sobreestima** la varianza y por tanto deja la z del lado conservador; y de doce pistas probadas, que alguna dé |z| > 2 por azar es esperable — "lleva comillas" salió con z = 2,97 sobre **23** preguntas y se descartó por eso, no por el resultado. La consulta se validó levantando un Postgres 16 local y cargando esos 1067 ítems, comprobando que devuelve los mismos números que el análisis hecho aparte en Python — no se mandó a ciegas. the fix was a second hunspell pass checking each half of the pair *on its own*, and only keeping a candidate when at least one half is NOT independently a valid word (a genuine split artifact always leaves one side as a non-word fragment, e.g. "evalua"/"informa"/"pre"/"o" in the hits below, whereas "Cat"/"cat"/"hoc" all check out as valid on their own even standalone) — this cut 745 candidates down to exactly 4 real ones, fixed in `supabase-arreglar-palabras-partidas.sql` (each scoped by exact `id`, one of them touching both `pregunta` and an `opcion` in the same row): "evalua ción" → "evaluación" and "informa ción" → "información" (PIR 22), "pre viamente" → "previamente" (PIR 22, same row as "informa ción"), and "respuesta o perante" → "respuesta operante" (PIR 21, confirmed by two sibling options in the same question that already spell "operante" correctly). **Un cuarto artefacto, y el primero de esta familia que sí se arregla en bloque: un número de página del PDF incrustado a mitad de frase con el punto suelto delante** — "…si la hipótesis de **. 4** investigación es verdadera…" (PIR 23, pregunta 11), que es como lo vio el usuario en la app. Contradice a propósito la nota de arriba de que no hay una sustitución masiva segura para la corrupción a mitad de frase: para *este* patrón sí la hay, porque el punto va **huérfano** (espacio delante), mientras que en un número legítimo va pegado a una cifra ("1.000 mg", "CIDI 3.0", "1.6 varones"). De ahí el regex de `supabase-arreglar-numeros-sueltos.sql`: `[[:space:]]+\.[[:space:]]*[0-9]+[[:space:]]+` → un espacio, en `pregunta`, `explicacion` y cada elemento de `opciones` (este último reconstruyendo el array con `with ordinality` + `order by`, porque el índice de cada opción es lo que apunta `correcta`). Toca **19 campos en 19 preguntas** de PIR 21 a PIR 25. Validado contra un Postgres 16 local con las 2102 filas cargadas, y la comprobación que vale no es "cambió 19" sino las cuatro de después: que ninguna pregunta cambiara de número de opciones ni de orden, que la diferencia entre el antes y el después sea **exactamente** aplicar ese regex y nada más, que no se perdiera ni un `[0-9]\.[0-9]` en todo el banco, y que una segunda ejecución devuelva 0/0/0 (es idempotente). Las iniciales con punto ("R. Sternberg", "La familia de J. está") no entran porque ahí el punto va pegado a la letra. Una pasada anterior y más estrecha se dejó fuera PIR 21 · pregunta 55, donde tras el número viene `(` en vez de una minúscula: moraleja de por qué el patrón se ancla en el punto huérfano y no en lo que lo rodea.
- **La autoevaluación se puede dirigir: origen, examen y tema.** Hasta aquí solo se podía tirar al azar de un examen, así que la app sabía perfectamente qué fallabas (`fallos`, `preguntas_progreso`, "Dónde fallas") y nada de eso servía para practicarlo. La pantalla de configuración de `Simulacros` tiene ahora tres controles que se combinan: **origen** (`origen`, chips con `styles.tabOrigenBtn`/`tabOrigenActivo` — Todas / Sin acertar / Falladas), el desplegable de **examen** de siempre y uno nuevo de **tema** (`temas`, que descarta los `TEMA_PLACEHOLDER` igual que `DondeFallas`, porque los exámenes transcritos del PDF no traían tema). "Sin acertar" es `!acertada` — lo nunca acertado, **incluido lo que no has visto**; deliberadamente NO es la definición de la pestaña "Pendientes" de `BancoPreguntas` (`veces === 0`), que deja fuera lo intentado-y-nunca-acertado: de ahí que el chip se llame distinto, para que dos criterios distintos no compartan nombre. "Falladas" es tener fila en `fallos` con `veces > 0`, la hayas acertado después o no. `Simulacros` recibe para esto dos props nuevas del raíz, `preguntasProgreso` y `fallos`. `filtradas` sustituye al antiguo filtrado en línea dentro de `start()`, y `disponibles` sale de su longitud, así que el contador ya refleja los tres filtros a la vez; un `useEffect` recorta `numPreguntas` cuando el cambio de filtro deja menos de las pedidas, y con 0 disponibles el botón se desactiva con un aviso en vez de empezar una tirada vacía (combinaciones como PIR 18 + un tema que no existe en ese examen son normales). Modo relámpago no se toca: sigue barajando todos los exámenes al margen de estos filtros.
- **Una autoevaluación a medias sobrevive a cerrar la app** (`claveTirada`/`leerTiradaGuardada`/`guardarTirada`/`borrarTirada`, a nivel de módulo junto a `lunesDeLaSemana`). Antes la tirada vivía solo en el estado de React: bloquear la pantalla o que Safari descartara la pestaña se llevaba por delante 30 preguntas. Se guarda en `localStorage` bajo `pir-tirada-<nombre>` (por usuario, no compartido entre cuentas del mismo móvil) y en la pantalla de configuración aparece una tarjeta "Tienes una autoevaluación a medias" con Continuar / Descartar. Se guardan **ids, no las preguntas enteras**, y se rehidratan contra `questions` al volver (`tiradaLista`, un `useMemo`): ocupa una fracción y nunca resucita el texto viejo de una pregunta corregida entre medias. La reconstrucción es todo-o-nada — si falta cualquier pregunta del pool, o el `idx` guardado cae fuera de rango, se descarta la tirada entera, porque rellenar huecos descuadraría los índices contra las respuestas ya dadas. Caduca a los 7 días (`MAX_EDAD_TIRADA_MS`). `poolOriginalIds` se guarda como `null` cuando coincide con `poolIds` (lo normal durante la tirada) para no duplicar los ~2100 ids del modo relámpago en cada escritura, y al restaurar se cae de vuelta en `poolIds`. **`seconds` queda fuera de las dependencias del efecto que guarda**: si no, escribiría en disco una vez por segundo; se persiste con cada respuesta, así que al retomar se pierden como mucho los segundos de la pregunta en curso. Relámpago también se retoma, con su `rachaViva` y su `recordPrevio` congelado; lo ya respondido no se vuelve a contar en Supabase porque `onStreakAnswer`/`onFallo`/`onRespuestaPregunta` se disparan al responder, no al terminar.
- **Desde "Dónde fallas" se practica directamente.** Cada fila lleva un enlace **Practicar** que salta a Autoevaluaciones con ese examen o ese tema ya elegido; hasta entonces la pantalla decía que ibas al 38% en algo y había que ir a buscarlo a mano. El aviso sube por `onPracticar` (`FilaAcierto` → `DondeFallas` → `MiPerfil` → raíz), donde `filtroPedido` guarda el filtro y `setSection("simulacros")` cambia de pestaña; `Simulacros` lo aplica en un `useEffect` y llama a `onFiltroAplicado` para que el raíz lo suelte — si no, volver a la pestaña lo reimpondría encima de lo que hubieras cambiado a mano. El filtro pasa antes por `aplicarFiltroPedido` (en `src/logica.js`, con pruebas): "Dónde fallas" agrupa por el `curso` y el `tema` en crudo, pero los desplegables no los listan todos — el de exámenes deja fuera las etiquetas que no son una edición ("Psicopatología", vía `esExamen`) y el de temas depende de si están incluidas las inventadas —, y un valor que no esté en su lista dejaría el `<select>` en blanco, así que se cae a "Todos". El origen se deja en "Todas" a propósito: es la lectura menos sorprendente de "practicar este tema", y los chips quedan ahí para acotar a "Sin acertar" si se quiere.
- **"Dónde fallas" (`DondeFallas` en `MiPerfil`, arriba del historial de fallos).** El % de acierto por examen (`curso`) y por tema (`tema`), para saber qué repasar. No necesitó nada nuevo en Supabase: sale de cruzar dos tablas que ya se escribían pero que no se enseñaban juntas en ningún sitio — `preguntas_progreso.veces` (intentos por pregunta) menos `fallos.veces` (fallos por pregunta) son los aciertos, y `agruparAciertos` los suma por la clave que se le pase. Se ordena de peor a mejor, que es el orden en el que conviene repasar. Decisiones que conviene no deshacer sin motivo: (1) lo que no has empezado queda fuera del ranking con `pct: null` en vez de contar como 0%, porque es ausencia de dato, no un mal resultado; (2) por tema se descartan los `Pregunta N` (`TEMA_PLACEHOLDER`), ya que los exámenes oficiales transcritos del PDF no traían tema y si no ensuciarían la lista entera, y se corta en `MAX_FILAS_TEMA` = 15; (3) la barra ya codifica la magnitud, así que el color solo marca lo flojo (<60%, `ACENTO`) en lugar de repintar un degradado de 4 tonos sobre lo que la longitud ya dice, y el número va en tinta, nunca en el color de la barra — todos los recuentos están escritos, así que nada depende del color ni del hover. El pie advierte de la limitación heredada del backfill: lo acertado antes de que existiera `preguntas_progreso` no dejó rastro (solo se guardaban los fallos) y figura como no empezado, y las filas recuperadas de `fallos` arrancan con intentos = fallos, o sea 0%, que es justo lo que consta de ellas.
- `Flashcards`: front/back cards (`flashcards.frontal`/`.posterior`, grouped by `mazo`) reviewed with a simplified SM-2 spaced-repetition algorithm (`calcularSM2` in `App.jsx`, same model Anki uses) — a card is "due" when `flashcards_progreso.proxima_revision` is null or `<=` today. Each review ends with one of 4 difficulty ratings (Otra vez/Difícil/Bien/Fácil, mapped to SM-2 quality 0/3/4/5 — see the bullet below for the naming and the per-button interval preview) which updates that user's `ease_factor`, `intervalo_dias`, `repeticiones` and `proxima_revision` for that card via `registrarRepasoFlashcard`. Before starting, the user picks how many due cards to do that round (`numTarjetas`, defaulting to `TAM_SESION_FLASHCARDS` = 20, same raw-while-typing/clamp-on-blur input pattern as `Simulacros`' cantidad field); `ordenarPorPrioridad` then orders the due pool so cards just reset by an "Otra vez" rating (`repeticiones === 0`) come first, other due reviews next (most overdue first), and never-seen cards last, before slicing to the chosen count — so the ordering itself reacts to the difficulty feedback already given, not just the next-due-date. **Flashcards are private per user, not a shared deck** (changed from the original single shared "Mi baraja" Anki import): `flashcards` has a `user_id` column (`supabase-flashcards-privadas.sql`, run after `supabase-enable-rls.sql`) and RLS restricts select/insert/update/delete to `auth.uid() = user_id`, so the query that fetches `flashcards` (a plain `.select("*")` with no client-side filter, same call as before) now transparently returns only the caller's own cards — nobody sees anyone else's. The original 271-card "Porcentajes/ prevalencias" deck (still loaded once via the bulk `insert` in `supabase-flashcards.sql`) was reassigned to the admin's account by that migration's backfill, so it became Pablo's personal starting deck rather than disappearing; everyone else starts with zero cards. `FlashcardEditableCard` no longer gates editing behind `user.isAdmin` (ownership itself is now the gate, enforced server-side by RLS) and has a "Borrar" button with an inline "¿Seguro? Borrar" confirm step, wired to `onDelete` → `deleteFlashcard`. The `mazo` field is a free-text label the card's owner picks per card (defaults to "General" if left blank) rather than a single deck name shared by the whole table.
- **Los cuatro botones de dificultad ahora significan cuatro cosas distintas.** `calcularSM2` era el SM-2 original (1987) tal cual, y ahí **Difícil, Fácil y Muy fácil daban EXACTAMENTE el mismo próximo día**: el intervalo se multiplicaba por el `ease` en los tres casos, y lo único que cambiaba era el propio `ease`, que tarda varios repasos en notarse. Marcar "Difícil" no te devolvía la tarjeta antes, que es justo lo que uno espera al pulsarlo — lo detectó el usuario ("veo que es igual que marques una que otra") después de que una ejecución del algoritmo lo pusiera negro sobre blanco. Ahora cada botón lleva su multiplicador, como Anki: Difícil `x1.2`, Fácil `xease`, Muy fácil `xease x1.3` (**superado** por los multiplicadores fijos x1/x2/x3/x4 del punto siguiente, que es lo que rige hoy; esto queda como el paso intermedio y el porqué). Sobre una tarjeta asentada (30 días, ease 2.5) eso da **1 / 36 / 75 / 103 días** en vez de 1 / 75 / 75 / 75. Una tarjeta nueva marcada "Muy fácil" se gradúa a 4 días en vez de repetirse mañana. También cambian los saltos de facilidad a los de Anki (`CAMBIO_EASE`: -0.2 / -0.15 / 0 / +0.15) en lugar de la fórmula original, que restaba **0.8** al fallar: con dos fallos la tarjeta quedaba clavada en el suelo de `EASE_MINIMO` (1.3) y, subiendo de 0.1 en 0.1, no había forma de rescatarla. Hay prueba de que se recupera. Y `Math.max(intervalo + 1, ...)` evita que acertar deje el intervalo igual, que con `x1.2` sobre 1 día pasaba. Efecto en lo ya existente: los `ease_factor` guardados se calcularon con la fórmula vieja, así que algunas tarjetas arrastran valores más bajos de lo que merecen; con los saltos nuevos se recuperan solos a base de acertarlas. **Y se llaman y se leen como los de Anki**: los nombres pasaron de "Muy difícil / Difícil / Fácil / Muy fácil" — dos parejas de sinónimos, donde lo que cambia de verdad es el intervalo y no el grado de agrado — a **Otra vez / Difícil / Bien / Fácil**, que nombran lo que va a pasar: "Otra vez" es la acción y no un juicio sobre uno mismo, "Bien" es el botón por defecto (el que se pulsa casi siempre) y "Fácil" es el premio, no un empate con "Bien". **Cada botón llevó un tiempo debajo el próximo repaso** (1 día / 36 días / 2 meses / 3 meses sobre una tarjeta asentada), sacado de llamar a `calcularSM2` con esa misma calidad, para que los botones no solo significaran cosas distintas sino que se *vieran* distintos sin tener que pulsar y volver días después. **Se quitó a petición del usuario** ("quitame la letra de los dias en el feedback, eso es informacion para ti no para el que la hace, que se vea solo facil, dificil, etc"): al repasar, lo que se decide es cómo de bien te la sabías, y poner el precio en días al lado de cada botón empuja a elegir por el calendario en vez de por eso. Ahora el botón es solo la palabra. Lo que sigue bajo los cuatro es una línea suelta ("Cada botón multiplica por 1, 2, 3 o 4. Nada se aplaza más de 60 días"), que explica el mecanismo sin pegarle una cifra a cada opción. `textoIntervalo` (en `src/logica.js`, con pruebas) se conserva y lo usa esa línea.
- **Cada botón multiplica el intervalo por 1, 2, 3 o 4, y nada pasa de 60 días (`MULTIPLICADOR`, `MAX_INTERVALO`, `dentroDelHorizonte` en `src/logica.js`, con pruebas).** Es el final de tres intentos y conviene saber por qué se descartaron los dos primeros. El SM-2 original daba el mismo día para Difícil/Fácil/Muy fácil; ponerle los multiplicadores de Anki (x1.2 / xease / xease*1.3) los separó, pero el número seguía saliendo del **factor de facilidad que arrastra cada tarjeta**, así que el mismo botón daba un día distinto en cada una y no había forma de saber a qué atenerse — además de irse a 3, 6 y 12 meses, inútil para una oposición. Un techo atado a `ajustes.fechaObjetivo` (la mitad de lo que quedara) corrigió lo segundo y no lo primero. La petición cerró las dos cosas de golpe: *"que sea en x1, x2, x3 o x4 respectivamente"* y *"olvídate de la fecha límite"*. Así que ahora `intervalo = max(1, intervalo) * {1,2,3,4}` y punto: sobre 9 días son 18 / 27 / 36, se predice de cabeza, y **la fecha objetivo no entra en el cálculo** (sigue existiendo, pero solo como plan de estudio en "Tu fecha" de Estadísticas). `ease_factor` se sigue **calculando y guardando** con los saltos de Anki (`CAMBIO_EASE`) aunque ya no decida el intervalo: es el poso del feedback y de ahí salen las "atascadas" (`EASE_ATASCADA`) de la pantalla de estadísticas — quitarlo rompería eso. "Otra vez" es x1 en el sentido de volver al primer peldaño (1 día), no de repetir el aplazamiento que llevara. **La decisión que no conviene deshacer: contra el techo no se recorta con `Math.min`, se encoge la escalera entera.** Truncar reintroduce la queja original — una tarjeta de 27 días daría 54 / 60 / 60 y "Bien" y "Fácil" volverían a ser el mismo botón —, así que se mira lo que daría "Fácil" y, si pasa del techo, se reducen las tres opciones en la misma proporción: el 2:3:4 queda intacto (30 / 45 / 60), solo que sobre una base más corta. La escalera se estabiliza en 45 días en vez de dispararse (1, 3, 9, 27, 45, 45…). Lo que quedó aplazado a 103 días con las fórmulas viejas se adelanta **al leer** (`dentroDelHorizonte` recorta solo `proxima_revision` y deja `intervalo_dias` como está para no falsear el historial; la próxima vez que la repases ya se guarda bien), así que no hubo que migrar nada en Supabase. `textoIntervalo` corta en días hasta `MAX_INTERVALO` para que todo lo que quepa se pueda comparar botón a botón, y bajo los botones se lee "Cada botón multiplica por 1, 2, 3 o 4. Nada se aplaza más de 60 días".

- **Tres añadidos que hacen que el repaso decida cosas, no solo las enseñe** (`mezclarTemas`, `sugerirAdelanto`, `planHastaObjetivo` en `src/logica.js`, con pruebas):
  1. **Se alternan los temas dentro de la sesión.** `empezar()` pasa lo ya elegido por `mezclarTemas` con `temaDeTarjeta` (primera etiqueta, y si no tiene, el mazo). Repasar agrupado por tema se siente más fácil y retiene peor. **No se baraja**: eso tiraría el orden por urgencia — se mira una `ventana` de 5 posiciones buscando otro tema, y si no lo hay cerca manda la urgencia. El orden es prioridad → cortar a la cantidad pedida → alternar, en ese orden.
  2. ~~**Se propone deshacer los picos de carga.**~~ **Retirado** (`sugerirAdelanto`/`PICO_MINIMO` borrados de `src/logica.js` con sus pruebas, y la tarjeta naranja del panel con ellos). Avisaba de un día que se disparaba en la previsión y ofrecía adelantar parte hoy. **El usuario lo rechazó** ("El mensaje de lo del domingo no me gusta... yo no hare todos los dias tarjetas"), y el motivo es de fondo, no de redacción: repartir la carga entre días futuros **presupone que repasas todos los días**. Quien estudia a ratos no tiene un calendario que alisar — tiene una cola que atender cuando se sienta. Lo sustituye el punto siguiente.
  3. **Fecha objetivo** (`ajustes.fechaObjetivo`, en `localStorage` con el resto de ajustes, no en Supabase: es preferencia de dispositivo). El cálculo que aporta algo no es "quedan 64 días", sino que una tarjeta tarda unos `DIAS_PARA_CONSOLIDAR` (30) desde que se estrena hasta que aguanta sola — así que hay una **fecha tope para estrenar tarjetas nuevas**, bastante anterior, y de ahí sale el "unas N al día". Pasada esa raya devuelve `nuevasPorDia: null` y la pantalla dice que toca rematar lo empezado, en vez de pedir un ritmo que ya no puede cuajar.
- **La fecha decide el ORDEN, no el permiso: siempre se puede repasar** (`colaDeRepaso` en `src/logica.js`, con pruebas; `cola` en `Flashcards`). El modelo de Anki da por hecho que repasas a diario: si hoy no vence nada, hoy no hay nada que hacer, y la pantalla decía "No te toca repasar ninguna tarjeta hoy. ¡Vuelve mañana!". Para quien estudia a ratos eso es **cerrarle la puerta justo el día que se ha sentado a estudiar** — y fue la queja ("yo no hare todos los dias tarjetas, ordenalos mas bien en funcion de orden para que vuelvan a salir una antes que otra"). `colaDeRepaso` devuelve **todas** las tarjetas del ámbito puestas en orden de turno: lo vencido delante (con lo marcado "Otra vez" por encima, vía `ordenarPorPrioridad`), luego lo nunca visto, y después lo que aún no toca **empezando por lo que vuelve antes**. Las fechas se siguen calculando igual y `proxima_revision` no cambia de significado: lo único que cambia es que ya no hace de portero. En la pantalla: con tarjetas vencidas sale "Te tocan N" y, si hay más en la cola, una línea que avisa de que pedir más sigue por las siguientes; **sin nada vencido ya no hay callejón sin salida**, sale "Hoy no vence ninguna, pero puedes seguir" con el mismo contador y el mismo botón. El tope del campo de cantidad pasa de las vencidas a la cola entera. **La contrapartida se dice, no se esconde**: adelantar recorta un poco el espaciado — es la misma frase que llevaba la tarjeta de los picos, que es donde seguía siendo cierta. Comprobado en un navegador en los dos casos: sin nada vencido se puede empezar y la primera que sale es la de `proxima_revision` más cercana; con dos vencidas de diez, el panel cuenta 2 y la primera es la más atrasada. **En los empates manda el azar, y esto no es un detalle**: si contestas "Fácil" a todas, todas se van al mismo día, y con un desempate estable el orden de la lista —siempre el mismo— decidía por su cuenta, así que las repasabas una y otra vez en la misma secuencia y acababas aprendiéndote el orden en lugar de la tarjeta (lo cazó el usuario: "si todos son faciles por ej, ahora no cambia el orden de repaso"). `ordenarPorPrioridad` y `colaDeRepaso` sortean una vez por llamada y **solo miran el sorteo cuando la fecha coincide**, así que la urgencia sigue mandando (hay prueba de las dos cosas, con un `azar` falso que va de mayor a menor para que un desempate estable se note). Y `empezar()` **vuelve a pedir la cola en vez de usar la del `useMemo`**: el memo solo se recalcula si cambian sus dependencias, así que sin eso empezar dos veces seguidas sin haber contestado nada daría el mismo orden exacto. Comprobado en un navegador con diez tarjetas en la misma fecha y cinco cargas seguidas: salieron primero la 5, la 8, la 4, la 8 y la 0. **Y el azar solo no bastaba, porque abre lo contrario**: con sorteo puro una tarjeta puede volver a tocarte sin que las demás hayan salido ("que no se repitan antes de que vuelvan a salir otras si tienen la misma dificultad"). Así que el desempate son **dos criterios en este orden: primero la que hace más que no ves (`ultima_revision`, que es un instante completo, no un día), y el sorteo solo cuando eso también empata** — lo nunca visto o lo repasado en el mismo instante. Es un reparto **sin reemplazo y sin guardar nada nuevo**: repasar una actualiza su `ultima_revision` y la manda al final de su grupo ella sola, así que la rueda da la vuelta entera antes de repetir. **Lo honesto sobre qué demuestra cada prueba, que aquí importa:** las pruebas de `tests/plan.test.mjs` sí fijan el mecanismo — sin el criterio nuevo fallan dos, y la que lo caza es una simulación de seis tarjetas empatadas y tres sesiones de dos **con la fecha clavada a propósito**, que es el caso difícil. La comprobación en navegador (seis tarjetas, tres sesiones de dos, contestando "Bien") sale limpia —las seis sin repetir— **pero también salía limpia sin el cambio**, porque contestar mueve `proxima_revision` y la propia fecha ya las separa; o sea que en el camino normal esto ya se cumplía por su cuenta y lo que añade el criterio es **la garantía para los empates**, no un arreglo de algo que se viera roto. Por eso esa prueba de navegador no se ha guardado en el repo: pasaría igual sin el código que dice comprobar.
- **Lo que fallas vuelve ANTES de acabar la sesión, como en Anki** (`PASOS_REPETICION`, `reinsertarEnSesion`, `tarjetasDistintas` en `src/logica.js`, con pruebas; `calificar` en `Flashcards`; `tests/repaso-repite.mjs`). Hasta aquí el feedback solo movía una fecha: marcabas "Otra vez" y la tarjeta que acababas de fallar no volvía hasta el día siguiente, con la respuesta ya olvidada otra vez. La petición fue explícita ("si fallo una, y la pongo muy dificil o dificil, cuelamela otra vez antes de acabar si hay mas faciles... el sistema tiene que detectar en tiempo real el feedback que le doy"). `sesion` deja de ser una lista que se recorre una vez y pasa a ser **una cola que crece sobre la marcha**: al puntuar, `reinsertarEnSesion` mete otra copia de la tarjeta más adelante — **"Otra vez" a 3 posiciones, "Difícil" a 8**, y si no quedan tantas por delante entra al final, que sigue siendo antes de acabar. "Bien" y "Fácil" devuelven la misma lista (identidad, así que no se reescribe el estado). **El retardo es el punto, no un detalle**: devolverla acto seguido no enseña nada porque la estarías leyendo, no recordándola; por eso vuelve con otras por medio. Se puede fallar la misma una y otra vez y volverá siempre — igual que Anki, y la salida es pulsar "Bien". Tres consecuencias que hubo que atar: el total de la cabecera **sube a mitad de sesión**, así que se explica de dónde sale ("Tarjeta 2 de 7 · 1 para repetir") en vez de dejar un número que cambia solo; el resumen usa `tarjetasDistintas` y no `sesion.length`, porque "has repasado 14 tarjetas" tiene que ser tarjetas y no pulsaciones; y bajo los botones se avisa de que lo marcado "Otra vez" o "Difícil" volverá a salir. Cada pulsación sigue escribiendo en `flashcards_progreso` y `flashcards_repasos`, igual que en Anki, así que la segunda vuelta recalcula el intervalo desde el estado ya actualizado (fallar y luego acertar deja la tarjeta en el primer peldaño, que es lo correcto). **La prueba de navegador aquí sí hace falta**: `reinsertarEnSesion` se prueba sola en `plan.test.mjs`, pero el bucle de la sesión vive en `App.jsx` y `npm test` no lo alcanza; `tests/repaso-repite.mjs` (`npm run build && node tests/repaso-repite.mjs`, como `humo.mjs`) marca la primera "Otra vez" y el resto "Bien", y comprueba que la fallada reaparece, que **no** reaparece inmediatamente, y que el resumen dice 6 y no 7. El montaje tiene un detalle que cuesta encontrar: el `upsert` de `flashcards_progreso` devuelve la fila y la app solo actualiza su copia local si llega, así que la ruta POST del test tiene que contestar con lo que se le manda.
- **Curva de retención** (`Retencion` dentro de `EstadisticasFlashcards`; cálculo en `src/logica.js`: `retencionGlobal`, `retencionPorSemana`, `retencionPorIntervalo`, `repasosPorDia`, con pruebas). Necesitó una tabla nueva, **`flashcards_repasos`** (`supabase-flashcards-repasos.sql`): `flashcards_progreso` guarda una fila por tarjeta con su estado actual, así que no había historia y sin historia no hay curva. Una fila por repaso, append-only — de ahí que sus políticas RLS sean solo select e insert. **Empieza a contar desde que se ejecuta**: lo anterior no se puede recuperar porque nunca se guardó, y la pantalla lo dice en vez de disimularlo. `registrarRepasoFlashcard` inserta la fila además de actualizar el progreso, guardando `calidad`, `acierto` (calidad >= 3, calculado al escribir y no deducido al leer: si cambia el umbral del algoritmo, lo ya registrado sigue significando lo mismo) e **`intervalo_antes`**, que es lo que permite el corte por distancia. La carga inicial pide solo los **últimos 90 días**, que es lo que dibuja la pantalla. Entra también en la cola de sin conexión (`flashcards_repasos` con `onConflict: "id"`, seguro por ser append-only); si la tabla todavía no existe el error **no** se encola, porque reintentarlo fallaría igual. Decisiones: una semana sin repasar sale con `pct: null` y un guion, **no como un 0%** — no repasar no es fallar, y la línea se corta ahí en vez de interpolar por encima de un dato que no existe (hay prueba); el objetivo de referencia es el **90%** de Anki, y el texto interpreta el número en las dos direcciones, porque estar muy por encima significa repasar de más, no ir mejor; y el corte **por intervalo** es el que de verdad acciona algo, ya que separa "estudio poco" de "se me espacian más de lo que aguanto".
- **Subpestaña "Estadísticas" dentro de un mazo** (`EstadisticasFlashcards`, con el cálculo en `src/logica.js`: `clasificarTarjeta`, `estadisticasFlashcards`, `agruparEstadisticas`, y sus pruebas). Convive con "Repasar" en un toggle `styles.tabOrigenBtn`/`tabOrigenActivo`, y **respeta el ámbito**: mazo abierto + etiquetas activas, así que las mismas chips filtran también las estadísticas. Lo que hay para calcular es el **estado actual** de cada tarjeta, no un historial: `flashcards_progreso` guarda una fila por tarjeta, no una por repaso, así que **no se puede dibujar la retención semana a semana** que enseña Anki — se dice en un pie, no se disimula. Lo que sí sale, y es lo que decide qué estudiar: `ease_factor` (el poso de TODO el feedback de dificultad dado en esa tarjeta), `intervalo_dias` (cuánto has consolidado) y `proxima_revision` (la carga que viene). Decisiones que conviene no deshacer: (1) **madura = intervalo >= `DIAS_MADURA` (21)**, el mismo corte que Anki, porque ver una tarjeta muchas veces no es sabérsela — aguantar tres semanas sí; (2) **`pctMaduras` se mide sobre las vistas, no sobre el total**, o añadir tarjetas nuevas hundiría el porcentaje y parecería que vas peor por estudiar más (hay prueba que lo fija); (3) **atascadas = `ease_factor <= EASE_ATASCADA` (1.8)**, que es el proxy de los "leeches" de Anki ya que no hay contador de lapsos, y el texto empuja a **reescribirlas**, no a repetirlas más; (4) los grupos se ordenan **por dificultad media ascendente**, lo que peor llevas arriba, y un grupo sin estrenar (`easeMedio === null`) se va al final en vez de colarse como lo peor. En lo visual: la barra de cada grupo dibuja el **% consolidado** y la dificultad va en número al lado — meter las dos como barra sería pintar dos magnitudes distintas con la misma forma; la previsión es una sola serie de un solo color, con el número escrito encima de los días con carga y el rojo `ACENTO` reservado a "hoy con atrasadas", que es estado y no magnitud; y la barra de madurez usa una rampa de un solo tono claro→oscuro porque son cuatro estados **ordenados**, con leyenda y todos los valores escritos.
- **Mazos are flat, one level, no nesting — a folder-browser detour was tried and rolled back.** Several rounds of UI experiments briefly turned `mazo` into a two-level folder system (a `"/"` in the string meant "lives inside this folder"), then let one card belong to several mazos at once sharing SM-2 progress (a `grupo_id uuid` column, `supabase-flashcards-grupo-id.sql` — the column is still in the DB, harmless and unused now, kept rather than migrated away per this repo's "leave dead artifacts, don't undo a migration" convention), then a "Mover" action to relocate a whole folder or a loose card into an existing one. Direct user feedback across that whole arc was consistently negative — "Estas haciendo un lio tremendo con los mazos carpetas y demas", "no me deja traspasar los mazos enteros... hazlo lo mas sencillo posible hay mucha cosa inutil", and finally the explicit rollback request: "Deja solo mazos y añade las tarjetas que estan dentro solo. Y no se pueden añadir mas mazos dentro. Si yo entro en un mazo, haz mas dinamico lo de añadir, y no me de opcion a añadirlo a otra carpeta, no de opcion a añadirlo en ninguno mas." All of that folder/multi-mazo/move machinery (`arbolCarpetas`, `statsDeCarpeta`, `carpetaNavegando`/`filtroCarpeta`, `FilaCarpetaEditable`, `SelectorMazosMultiple`, the "Mover" flows on both mazos and individual cards) was removed outright — this is the one place in `Flashcards` where dead code was actually deleted rather than left behind, since leaving it would keep reintroducing the confusion that was the whole complaint. The current model: every `mazo` value is one flat entry in a single-level list (a `"/"` in a name, if one somehow exists from the old convention, is just a literal character now, not a separator); `renombrarMazo(viejo, nuevo)`/`eliminarMazo(nombre)` lost their `cascada` parameter (always exact-match on `mazo`); `addFlashcard`/`addFlashcardsBulk` insert into exactly one mazo, no array. `deleteFlashcard`/`eliminarMazo` still do the `grupo_id`-aware orphan cleanup of `flashcards_progreso` (harmless leftover from the multi-mazo detour, and still correct for any card that happens to have `grupo_id !== id` from that brief window) — the only surviving trace of that whole arc.
- **Adding a card is scoped to wherever you are, no destination picker at all.** `NuevaFlashcard`/`ImportarFlashcards` take a `mazoFijo` prop: inside an already-selected mazo, it's set and the card goes straight there — no mazo field is shown, and per the "haz mas dinamico" request the form does *not* close after saving (inputs clear and refocus instead), so several cards can be added back-to-back without reopening anything. Only at the root mazo list (no `mazoFijo`, since there's no "current mazo" to imply) does it ask for a name — that's exclusively how a brand-new mazo gets created; there is deliberately no way to add a single card to more than one mazo. Moving one *after* the fact is a separate thing and does exist: `FlashcardEditableCard` has a **Mover** button next to Editar/Borrar (only when another mazo exists), opening the same plain `<select>` of the other mazos as the whole-mazo send below — it calls `updateFlashcard(id, { mazo })`, which patches only the fields it is handed (`frontal`/`posterior` and/or `mazo`).
- **Etiquetas per card (`flashcards.etiquetas`, a `text[]`).** Added by the user directly in Supabase from a different conversation (`supabase-flashcards-etiquetas.sql` is the repo's record of it, written after the fact; the column is `not null default '{}'` with a GIN index for "contains" filtering). They are deliberately **transversal to the mazo** — the same tag can sit on cards of different mazos — so they answer "repasar todo lo de este tema" without reorganizing anything, which is the thing the folder detour kept failing at. Kept as an array on the row rather than a tags table + join table: few per card, always read with the card, and the GIN index already covers the only query needed. In the UI a card's tags are picked with `SelectorEtiquetas` (shared by `NuevaFlashcard`, `ImportarFlashcards` and `FlashcardEditableCard`'s edit form): every tag you already use anywhere — `todasLasEtiquetas`, computed across all your cards, not just the open mazo — shows as a chip you tap to add, the ones already on the card are chips you tap to remove, and the text field is only for coining a new one (Enter adds it, parsed by the module-level `parsearEtiquetas`, which trims, drops empties and dedupes). Tapping beats retyping here on purpose: free typing was the first version and it invites "porcentajes" and "Porcentajes" living side by side. `ImportarFlashcards` applies one set to the whole pasted block, and `addFlashcard`/`addFlashcardsBulk`/`updateFlashcard` pass the array straight through. In `NuevaFlashcard` the tag selection is the one thing **not** cleared after a save (frontal/posterior are), so you pick "porcentajes" once and add ten cards under it. Reading them: each row in the card list shows its tags as chips (`styles.etiquetaTarjeta`), and above the review panel a "Repasar solo estos temas" chip row ("Todos" + one per tag present in the current scope, `styles.chipEtiqueta`/`chipEtiquetaActiva`) drives `etiquetasActivas` — an array, since the ask was to filter by "las etiquetas que yo quiera": chips accumulate and a card matches if it carries **any** of them (or, not and — requiring all of them at once would land on zero cards almost every time, when the point is reviewing those topics together). It narrows the due count, "Empezar repaso" and the card list alike. `etiquetasDelMazo` only lists tags present in what you are currently looking at, and a `useEffect` drops any active tag that stops existing there (e.g. after switching mazo). This is Flashcards-only — explicitly "SOLO PARA FLASHCARDS, LAS AUTOEVALUACIONES SE DEJAN COMO ESTAN". `mazo-esquemas-young.txt` en la raíz es el único mazo que el repo guarda como texto: las 18 tarjetas de "esquema → dominio" de la terapia centrada en esquemas de Young, en el formato `frontal;posterior` que lee `ImportarFlashcards`. **No es una migración y no se mete en Supabase desde aquí** — las flashcards son privadas por cuenta (RLS por `user_id`) y este contenedor no alcanza la base de datos, así que el mazo se crea pegando ese bloque en "Importar tarjetas" desde la propia app. Se conserva para poder rehacerlo sin volver a transcribir la diapositiva.
- **Un color y un icono por mazo, para distinguirlos de un vistazo cuando hay muchos** (`supabase-mazos-estilo.sql`; `indiceEstilosMazo`/`estiloDeMazo`/`estiloTrasRenombrar` en `src/logica.js`, con pruebas; `COLORES_MAZO`/`ICONOS_MAZO` y `SelectorEstiloMazo` en `App.jsx`). **Hizo falta una tabla aparte porque un mazo no es una entidad**: `mazo` es solo una etiqueta de texto repetida en cada fila de `flashcards`, y la lista sale de agrupar — meter el estilo en `flashcards` obligaría a escribirlo en todas las tarjetas y a decidir qué pasa si no coinciden. La tabla tiene clave `(user_id, mazo)` y las mismas cuatro políticas privadas que `flashcards`. **Lo que se guarda es la CLAVE, no el valor** ("acento", "Brain"), así que la base no sabe nada de la paleta ni de lucide: retirar una opción del catálogo mañana no deja una fila ilegible, ese mazo vuelve a su aspecto por defecto — por eso `estiloDeMazo` valida contra los catálogos que se le pasan en vez de fiarse de lo guardado (hay prueba). Decisiones: (1) **todo es opcional y decorativo** — sin fila, el mazo se ve exactamente como antes, y si la migración no se ha ejecutado la consulta llega con error y se queda vacía sin romper nada; (2) quitar color e icono **borra la fila** en vez de dejarla con dos nulos; (3) **al renombrar, el estilo sigue al mazo**, y como "enviar a otro mazo" es renombrar para coincidir con uno existente, **si el destino ya tenía estilo manda el suyo** (`estiloTrasRenombrar`), que es lo que uno espera al fundir dos; (4) al borrar un mazo se borra su estilo, aunque una fila huérfana sería inofensiva; (5) **los ocho colores son oscuros a propósito**, porque el fondo de las tarjetas es crema y un tono claro no se distingue; los doce iconos están elegidos por asignaturas del PIR, con `Percent` porque el mazo que ya existe es el de porcentajes. La consulta va en el mismo `Promise.all` del arranque, así que no cuesta otra ida y vuelta. Comprobado manejándolo en un navegador: abrir el selector, elegir verde y cerebro, guardar — la app manda `{mazo, icono, color}` y la fila queda con borde izquierdo `#2E7D46` de 4 px y el icono de cerebro en ese verde, mientras el otro mazo no se toca. **Lo que NO se ha podido probar desde aquí**: que el `upsert` con `onConflict: "user_id,mazo"` acierte contra Supabase, porque el cliente no manda `user_id` (lo pone el `default auth.uid()`) y este contenedor no alcanza la base.
- **Intro o espacio revelan la tarjeta, y con la respuesta a la vista sale un lápiz para corregir la errata que acabas de ver.** Dos cosas pequeñas con una trampa cada una. **El atajo**: un `keydown` en `window`, dentro de `Flashcards`, colocado **después de todos los `useState` y antes de cualquier return temprano** (un hook no puede ser condicional, y el orden importa — ver la regla de más abajo sobre el `useEffect` que tumbó la app). Tres guardas que no conviene quitar: no se dispara si el foco está en un `input`/`textarea`/`select` ni en nada editable, **o el espacio que escribes en el formulario de corrección revelaría en vez de escribirse**; lleva `preventDefault` porque el espacio desplaza la página; y **solo revela, nunca vuelve a ocultar**, que sería desconcertante justo cuando vas a pulsar una dificultad. Con Intro sobre un botón se deja pasar, para no pisar al botón. **La corrección en línea**: botón discreto ("Corregir esta tarjeta") que solo aparece con la tarjeta revelada, porque es para la errata que se ve al repasar, no una acción del repaso. **No reinicia la memoria, y sale gratis por construcción**: `updateFlashcard` solo escribe en `flashcards` —nunca en `flashcards_progreso`— y el progreso va indexado por `grupo_id || id`, que no cambia al editar el texto; el propio panel lo dice para que no dé miedo usarlo. El detalle que sí hubo que resolver: **`sesion` es una foto de las tarjetas tomada al empezar**, así que tras guardar hay que parchear también esa copia o seguirías viendo la errata hasta la siguiente sesión. Comprobado manejándolo en un navegador: Intro revela y la página no se desplaza; escribir un espacio dentro del campo lo escribe en vez de revelar; al guardar sale un `PATCH` a `flashcards` con solo `frontal`/`posterior`, **`flashcards_progreso` no se toca**, y la tarjeta se ve corregida al momento.
- **"Tarjeta a tarjeta": una cuadrícula en Estadísticas, un recuadro por tarjeta con su texto a la vista y una franja de color arriba, el último botón que pulsaste en ella** (`CuadriculaTarjetas`, `TANDA_CUADRICULA`, `ORDEN_CUADRICULA` en `App.jsx`; `ultimaCalificacionPorTarjeta`/`estadoCuadricula` en `src/logica.js`, con pruebas). Las barras de arriba dan medias; esto dice **qué tarjeta concreta** se atraganta, sin entrar a repasarla. **El dato no estaba**: `flashcards_progreso` guarda el estado actual pero no qué botón se pulsó, y la consulta de `flashcards_repasos` pedía solo `acierto, intervalo_antes, creado_en` — hubo que añadir `flashcard_id, calidad` a esa misma consulta (sin ida y vuelta extra). **De ahí que haya tres estados y no dos, y no conviene fundirlos:** `nueva` (sin fila de progreso), `sin-registro` (repasada, pero su repaso es anterior a que existiera la tabla de historial o más viejo que los 90 días que se descargan) y la calificación 0/3/4/5. **Pintar `sin-registro` de gris sería mentir**, porque esa tarjeta sí ha salido: su franja va a rayas y un pie lo explica; se colorea sola en cuanto vuelva a repasarse. **La primera versión eran cuadrados de 17 px con el texto en el `title`, y se rechazó**: cabían cientos de un vistazo, pero desde fuera no se sabía de qué tarjeta era cada color, que es justo lo que se viene a mirar. Ahora el texto va DENTRO (`frontal` a tres líneas con `-webkit-line-clamp`, una raya, y `posterior` a dos), el `title` se queda de respaldo para leerlo entero, y el color es una **franja de 5 px arriba y no el relleno** — con el recuadro pintado entero el texto no se lee. Se ordena de **peor a mejor** (`ORDEN_CUADRICULA`: 0 → 3 → 4 → 5 → sin-registro → nueva, con `sort` estable para no perder el orden del mazo dentro de cada color), porque se pinta de `TANDA_CUADRICULA` = 60 en 60 con un "Ver más" y dejar las atascadas en la página tres es esconderlas; es además el orden en el que conviene repasar, igual que en "Dónde fallas". Ojo con el 0: `estadoCuadricula` comprueba `typeof calidad === "number"`, porque un `if (!calidad)` trataría "Otra vez" como ausencia de dato (hay prueba). Comprobado en un navegador con las ocho combinaciones montadas a mano, a 420 y a 900 px, incluyendo un repaso viejo y otro nuevo de la misma tarjeta para ver que manda el reciente: la leyenda cuenta 2/1/2/1 + 1 sin registro + 1 sin estrenar y las rojas salen primero.
- **Sending a whole mazo's cards into another existing one.** Immediately after the rollback above, the user corrected the "no move action anywhere" framing ("El ultimo punto esta mal, si que tiene que haber forma de mandar mazos enteros a otro de manera sencilla") — a *whole-mazo* send was still wanted, just not the folder/typing-based version that got removed, and not a per-card one. `FilaMazoEditable` (the row for each mazo in the root list) gained a third icon next to Renombrar/Borrar — `FolderInput`, "Enviar a otro mazo" — only shown when at least one other mazo exists (an `otrosMazos` prop, `mazos` filtered to exclude the row's own name). - **El banco de preguntas se guarda en el navegador (`src/cachePreguntas.js`), no se descarga en cada carga.** Las ~2100 preguntas con sus opciones y explicaciones son varios megas que viajaban enteros cada vez que alguien abría la app. `obtenerPreguntas()` (junto a `fetchTodasPreguntas` en `App.jsx`, y lo que usa ahora la carga inicial) lee la copia local y contrasta con una consulta de **solo recuento** (`select("id", { count: "exact", head: true })`, que no trae ni una fila): si el número cuadra y la copia tiene menos de `MAX_EDAD_CACHE_MS` (24 h), no se descarga nada. El recuento detecta altas y bajas, pero **no** ediciones de texto — de ahí el límite de un día, que es lo que tarda como mucho en llegar una corrección de las que se hacen por SQL; `addQuestion`/`updateQuestion`/`deleteQuestion` llaman además a `borrarPreguntasCache()`, para que al admin sus propios cambios no le queden desfasados. Efecto secundario buscado: si el recuento falla por falta de red, o la descarga se corta, se devuelve la copia guardada en vez de dejar la pantalla vacía — la app abre sin cobertura, aunque lo que se responda entonces no se guarde. IndexedDB y no `localStorage`: este ronda los 5 MB (demasiado cerca del tamaño del banco) y es síncrono, así que serializarlo bloquearía la interfaz justo en el arranque. Todo el módulo devuelve `null`/`false` al fallar en vez de lanzar, para que navegación privada, almacenamiento lleno o cookies bloqueadas degraden a "descargar como siempre". **Y desde `supabase-preguntas-actualizado-en.sql` el recuento ya no decide solo: se pide también un sello.** El límite de 24 h no arreglaba el agujero, solo acotaba cuánto duraba — una corrección de texto por SQL no cambia ningún número, así que era invisible hasta que caducaba la copia. La migración añade `preguntas.actualizado_en` **con un trigger `before update`**, que es la pieza imprescindible: un `default now()` solo actúa al insertar y lo que hay que detectar son precisamente los `update`. `sondearBanco()` manda ahora las dos consultas baratas en paralelo (el recuento de siempre y `select("actualizado_en").order(…desc).limit(1)`, una fila), y `hayQueDescargar`/`selloDeFilas` (en `src/logica.js`, con pruebas) deciden. **Con sello no se caduca por tiempo**: si coincide, la copia es exacta, y bajar los ~2 MB una vez al día solo gastaría datos. Tres decisiones que conviene no deshacer: (1) **el sello que se guarda sale de las filas descargadas, no de la sonda** — si una corrección entra entre la sonda y la descarga, guardar el de la sonda dejaría esa copia marcada como al día **para siempre**; (2) el recuento sigue mandando por encima del sello, porque un `delete` puede dejar el sello igual; (3) **sin sello se cae al criterio viejo** (recuento + 24 h), que es lo que pasa con la migración sin ejecutar o si la consulta falla, y también fuerza una descarga en las copias guardadas antes de esto, que no lo traen. Comprobado en un navegador de verdad con `tests/cache-banco.mjs` (`npm run build && node tests/cache-banco.mjs`, igual que `humo.mjs` y tampoco lo coge `npm test`), que **cuenta las peticiones del banco completo** en cuatro escenarios sobre el mismo contexto de navegador —para que IndexedDB sobreviva de una carga a la siguiente—: primera visita descarga y guarda el sello; segunda sin cambios manda la sonda y **no** descarga; con el sello cambiado y el mismo recuento descarga (que es el caso que no se arreglaba); y con la consulta del sello devolviendo un 400 ("column does not exist") la app abre igual y no entra en bucle. Dos trampas que costó encontrar: en Playwright **gana la ruta registrada después**, así que el comodín `**/rest/**` va primero o se come la de `preguntas`; y el patrón `preguntas*` también pilla `preguntas_progreso`, así que hay que mirar el nombre exacto de la tabla o se cuentan peticiones ajenas como descargas. **Trampa al comprobar el trigger, que costó un susto:** el editor SQL de Supabase corre todo el bloque en **una sola transacción**, y `now()` en Postgres devuelve la hora de **inicio de la transacción**, no la del instante — así que un `update` de prueba metido en el mismo bloque que el `alter` escribe **el mismo valor** que el `default now()`, y `count(distinct actualizado_en)` sale 1 aunque el trigger esté funcionando. Reproducido en un Postgres 16 local: en una sola transacción da 1 y **la fila actualizada queda con la misma marca que una que no se tocó** (que es la prueba de que el trigger sí disparó); con el update en su propia transacción da 2. La comprobación del fichero dice ahora que va en una ejecución aparte. No afecta a producción, donde cada corrección es su propia transacción, posterior a la descarga que tenga el móvil. **La paginación de la descarga no era estable, y la copia local no se validaba.** Investigando un fallo del usuario (tres tarjetas del Banco que no se abrían al tocarlas y que además salían en toda búsqueda, sin contener lo buscado) se encontraron dos cosas que estaban mal por su cuenta, aunque **no está confirmado que sean la causa de ese síntoma**. (1) `fetchTodasPreguntas` paginaba con `.range()` ordenando **solo por `created_at`**, que no define un orden: el banco se cargó en bloque y cientos de filas comparten el mismo instante, así que Postgres puede devolver una misma fila en dos páginas y dejarse otra fuera — y el **recuento total sigue cuadrando**, de modo que ni la comprobación de la caché lo detecta. Se añade `.order("id")` como desempate, que es único. (2) `leerPreguntasCache` aceptaba lo que hubiera guardado; ahora pasa por `bancoUsable` (en `src/logica.js`, con pruebas), que exige `id` e enunciado de texto y `opciones` como lista de textos, y **rechaza ids repetidos** — la huella justamente de esa paginación inestable, que además produciría dos tarjetas con la misma clave de React. Es **todo o nada**, igual que `reconstruirTirada`: una fila mala tira la copia entera y se vuelve a descargar, porque colar la lista a medias es peor que gastar una descarga. `guardarPreguntasCache` aplica el mismo filtro, o una copia mala sobreviviría a los reinicios. Dos escenarios nuevos en `tests/cache-banco.mjs` lo comprueban contando descargas. **Lo que se probó y se descartó, para no repetirlo:** envolver la lista en un `<div key={origen|termino}>` para que React la reconstruyera al cambiar la búsqueda — medido con la CPU 4× más lenta y las 2102 coincidiendo, **pasa de 48 ms a 141 ms por tecla**, que ya se nota; no compensa pagarlo por una hipótesis. También se descartaron, con pruebas en navegador, que el problema fuera que algo tapara la zona de arriba (`elementFromPoint` dice que el toque llega a la tarjeta) y que las claves repetidas impidieran abrir una tarjeta (se abren igual).

- **Velocidad: las consultas de arranque van en paralelo y el Banco se pinta a tandas.** Las dos cargas iniciales (`cargarDatosApp` en el raíz, y el efecto de datos personales) hacían cuatro `await` en fila cada una — ocho idas y vueltas encadenadas a Supabase antes de poder pintar. Ahora cada grupo va con `Promise.all`, así que tardan lo que la más lenta en vez de la suma. No cambia el manejo de errores: supabase-js resuelve con `{data, error}` en vez de rechazar, así que el `throw` del error de `ranking` sigue igual, y `obtenerPreguntas()` (que sí puede lanzar) se comporta como antes. `BancoPreguntas` renderizaba `filtered.map(...)` entero: ~2100 `PreguntaCard` en el DOM cada vez que se abría el overlay, con el consiguiente tirón en el móvil. Ahora pinta de `TANDA_BANCO` en `TANDA_BANCO` (40) con un botón "Ver más (N restantes)", y un `useEffect` vuelve a la primera tanda al cambiar de pestaña o de búsqueda. El filtrado y el buscador siguen mirando la lista completa — solo se dibuja menos, no se esconde nada.
- **Lo respondido sin cobertura no se pierde (`src/colaPendientes.js`).** La app ya abría sin red gracias a la caché del banco, pero lo que se contestara ahí se evaporaba. Ahora, cuando una escritura falla **por red** (`esFalloDeRed`: `navigator.onLine === false` o un mensaje tipo "Failed to fetch"/"Load failed"), el estado local se actualiza igual — la pantalla sigue contando bien — y la fila se apunta en `localStorage` bajo `pir-pendientes-<nombre>`. Un rechazo del servidor (RLS, datos) **no** se encola: reintentarlo fallaría igual y taparía el fallo real. La decisión de diseño que lo hace seguro: **se guarda la fila tal y como debe quedar, no la acción para repetirla**. Repetir acciones obliga a saber contra qué estado se aplicaron, y dos respuestas encoladas leerían el mismo contador y se pisarían; una fila ya calculada se sube tal cual y da el mismo resultado se suba una vez o tres. Cada respuesta nueva sobrescribe la fila encolada de esa pregunta, que ya lleva lo anterior acumulado. `rachas` es la excepción de forma: una sola fila por usuario sobre la que `registrarAcierto` y `registrarProgresoDiario` **funden** campos (`conFila` hace merge en ese caso, no reemplazo), y lo que se encola es la fila completa (`{...actual, ...payload}`), no el trozo parcial que se manda normalmente. Cubre `fallos`, `preguntas_progreso`, `flashcards_progreso` y `rachas`; `ranking` queda fuera a propósito (nadie lo lee) y los duelos también, que sin red no se juegan igualmente. La sincronización vive **dentro del efecto que carga los datos personales**, no en uno propio, para que no compitan: subir primero y que luego la carga pisara el resultado con lo que el servidor tenía antes sería una carrera; también escucha el evento `online`. Al arrancar, lo pendiente se superpone a lo que venga del servidor, porque tras recargar sin red allí aún no consta. Si la red se corta a mitad de la subida se corta el bucle (`break`) y lo que falta queda para el próximo intento; si el servidor rechaza una fila se descarta, para que no bloquee la cola para siempre. En la cabecera aparece una píldora naranja "N sin guardar" (`CloudOff`) mientras haya cola. Contrapartida asumida y consciente: dos dispositivos con la misma cuenta, uno sin red, al reconectar pisarían lo del otro — resolver conflictos campo a campo no compensa para un uso de una persona y un móvil.

La tabla `ranking` se escribía en cada modo relámpago y **no la leía nadie**: el componente `Ranking` pinta `rachas`, y el estado `ranking` del raíz no se pasaba a ningún sitio. Se ha quitado `submitScore`, la prop `onFinish` de `Simulacros`, el estado `ranking` y su consulta en el arranque — una ida y vuelta menos al abrir. También cae `submitting`, que solo existía para guardar esa subida. La tabla se queda en Supabase como historia, según la costumbre de este repo de no deshacer migraciones.

- **Red de seguridad contra la pantalla en blanco del icono de la pantalla de inicio.** Síntoma real, y costó una tarde: la web abría bien en Safari pero desde el icono añadido a la pantalla de inicio salía el fondo y nada más. Causa: ese icono guarda su propia copia de `index.html`, y tras un despliegue el bundle cambia de nombre (`index-<hash>.js`), así que la copia guardada apunta a un fichero que ya no existe — el módulo no carga, React no monta, y **no se ve ni un error**. Tres capas: (1) `vercel.json` marca `/` y `/index.html` como `must-revalidate`, para que la página de entrada no se sirva de una copia vieja; (2) `#root` ya no nace vacío, trae un "Cargando AUTOPIR…" que React sustituye al montar; (3) un script en `index.html` comprueba a los 8 s la bandera `window.__autopirArranco` (que pone `main.jsx`) y, si React no montó, fuerza **una** recarga con un parámetro `_r=<ahora>` que se salta la copia guardada — una sola vez, con `sessionStorage` de guarda para no entrar en bucle — y si tras esa recarga sigue sin arrancar, escribe qué hacer (borrar el icono y volver a añadirlo). El parámetro se añade respetando los que ya haya, para no romper los enlaces de invitación `?c=CODIGO`. Comprobado con Playwright en los dos caminos: con el JS disponible el cartel desaparece, y bloqueando `**/assets/*.js` se ve la recarga única y el mensaje final.
- **Y la causa de esa pantalla en blanco, arreglada de raíz: el bundle ya no lleva hash en el nombre** (`build.rollupOptions.output.entryFileNames: "assets/app.js"` en `vite.config.js`, más una reescritura en `vercel.json`). Las tres capas de arriba son paliativos —revalidar, avisar, recargar una vez—: la copia del `index.html` que guarda el icono sigue pidiendo `index-<hash viejo>.js`, y ese fichero no existe después de un despliegue. Volvió a pasar ("Ahora no me abre la web", fondo y nada más, desde el icono) y el usuario tuvo que esperar a que alguien lo mirara, así que se ataca el mecanismo: **con nombre fijo, un `index.html` viejo pide un fichero que siempre existe y que además trae el código de hoy**. La contrapartida, asumida: sin hash no se puede cachear para siempre, así que `vercel.json` extiende el `max-age=0, must-revalidate` a `/assets/(.*)` — un 304 por arranque, que no se nota. **La reescritura es lo que rescata los iconos YA rotos** (`/assets/(.*).js` → `/assets/app.js`): las copias guardadas antes de este cambio siguen pidiendo un nombre con hash, y sin ella habría que borrar el icono y volver a añadirlo. En Vercel el sistema de ficheros se mira ANTES que las reescrituras, así que `/assets/app.js` se sirve tal cual y solo caen en la reescritura los nombres que ya no existen; y aunque ese orden fuera al revés, el patrón reescribe `app.js` a sí mismo, así que no rompe nada en ningún caso — por eso se eligió así y no con un patrón más fino. Comprobado con `tests/rescate-bundle.mjs` (`npm run build && node tests/rescate-bundle.mjs`, igual que `humo.mjs` y tampoco lo coge `npm test`), que levanta un servidor que emula ese orden de rutas, sirve a propósito un `index.html` viejo apuntando a un hash inexistente, y comprueba que `window.__autopirArranco` acaba en `true`.
- **Entrar y registrarse también tienen límite de tiempo.** El arreglo del arranque cubría la carga inicial, pero no el login: si `signInWithPassword` se queda colgada, el botón se queda girando indefinidamente y por fuera es "le doy a Entrar y no pasa nada" — exactamente la misma pantalla muda de antes, en otro sitio. `handleLogin`, el `fetch` a `/api/registro` de `handleSignup` y el `signInWithPassword` posterior al alta van ahora envueltos en `conTiempoLimite`, y el error se traduce con `mensajeDeCarga`. Un error real de credenciales sigue diciendo "Usuario o contraseña incorrectos": el mensaje de red solo sale cuando el servidor no contesta. En el caso del alta, si la cuenta se creó pero el login posterior se agota, se traga el fallo a propósito y `AuthScreen` enseña su "Cuenta creada, ya puedes entrar", que es lo cierto.
- **Un `useEffect` colocado encima del `useState` que lee tumba la app entera, y `npm test` no lo ve.** Pasó de verdad y costó media tarde: el efecto de `filtroPedido` en `Simulacros` quedó escrito **antes** de `const [state, setState] = useState("config")`, y como el array de dependencias (`[filtroPedido, state, cursos, temas]`) se evalúa en el momento de llamar a `useEffect`, se tocaba `state` antes de su declaración: `ReferenceError: Cannot access 'state' before initialization` en cada dibujado de la pestaña que se abre al entrar. React desmonta el árbol entero, y desde fuera es "entro y se queda el fondo crema". `npm run build` no lo ve (es válido sintácticamente), `npm test` tampoco (no dibuja), y el `no-undef` de ESLint tampoco (la variable existe). **Regla: en un componente, los efectos van después de todos los `useState`.** El efecto vecino que llama a `setNumPreguntas` se libraba por casualidad, porque esa llamada está dentro del callback y no en las dependencias. Dos redes montadas a raíz de esto: un **error boundary** en `main.jsx` (`Salvavidas`) que enseña el mensaje y las primeras líneas de la traza **en pantalla**, porque desde un iPad no hay consola y sin eso el fallo es invisible — de hecho fue él quien delató este bug; y `tests/humo.mjs`, que abre el `dist` en un navegador con una sesión fingida y Supabase respondiendo listas vacías, y falla si aparece "Algo se ha roto" o no se pinta la pantalla de dentro. No lo ejecuta `npm test` (que solo coge `tests/*.test.mjs`): se lanza con `npm run build && node tests/humo.mjs`, y en este contenedor con `PLAYWRIGHT_CHROMIUM=/opt/pw-browsers/chromium-1194/chrome-linux/chrome` delante. **Conviénelo correr siempre que se toque el arranque o el orden de los hooks.**

- **Security hardening for sharing with a small group:** `supabase-enable-rls.sql` (one-off, run by the user in the Supabase SQL editor like the other `supabase-*.sql` files) enables Row Level Security on all 10 tables and requires an authenticated Supabase session for virtually every read/write — before this, the client-exposed anon key alone allowed full read/write/delete on every table with no login at all. `preguntas`/`flashcards` writes (insert/update/delete on `preguntas`, update on `flashcards`) are further restricted to the admin's synthesized email (`auth.email() = 'pabloadmin@ruta-pir.local'`), mirroring the existing client-side `isAdmin` gating but now enforced server-side too. `ia_uso` is the one exception left open to the `anon` role: it's only ever touched by `api/generar-preguntas.js`, a serverless function that creates its own Supabase client from the anon key without forwarding the caller's session, so it always acts as `anon`, never `authenticated`. What RLS does **not** cover: no table has a `user_id`/`auth.uid()` column, so rows are all keyed by the free-text `name` field — an authenticated user could in principle read/write another user's `rachas`/`fallos`/`favoritos` row by calling the REST API directly (not through the UI). Fixing that fully needs a schema change (a `user_id` column plus rewritten policies and client queries), judged out of scope for now given the small trusted audience — **since closed** by `supabase-vincular-datos-personales.sql` (run after `supabase-enable-rls.sql`): adds a `user_id uuid references auth.users(id) default auth.uid()` column to `rachas`/`fallos`/`favoritos`/`flashcards_progreso`, backfills it for existing rows by matching `name` against `auth.users.raw_user_meta_data->>'username'` (case-insensitively, with a special-cased `name = 'Pablo'` → username `pabloadmin` since the admin's display name and login username differ), then replaces the earlier `*_auth` policies with `auth.uid() = user_id` checks on insert/update/delete (and on select too for `fallos`/`favoritos`/`flashcards_progreso`, which are purely personal with no shared display) — `rachas` keeps open select since Ranking/Logros show everyone's streaks. No client code changes were needed: `user_id` populates itself via the column `default` on insert, and upserts' `ON CONFLICT DO UPDATE` never touches it after that. Deliberately left out: `duelos`/`duelo_respuestas` (shared state between two named players, doesn't fit a single `user_id` owner column without a larger redesign) and `ranking`/`preguntas`/`flashcards` (already correctly shared/admin-gated, no change needed). `supabase-comprobar-admin.sql` is a read-only check for whether anyone besides the intended admin has registered under (or near) the `pabloadmin` username/email. Enabling RLS required a companion code fix first: the effect that loads `preguntas`/`ranking`/`rachas`/`flashcards` (in the root `AcademiaPIR` component) used to run exactly once on mount, before any login, so under RLS a first-time login/signup in a fresh browser would see those go empty and never recover without a manual refresh; the effect now tracks whether a session existed at that initial load and, if the auth state later transitions from no-session to a session (a fresh login/signup), re-runs the same fetch once now that the client is authenticated. Real signup **used to be** wide open (no invite gate) — anyone who found the app's URL could self-register and use it fully. Closed by a **server-side invite code** (`api/registro.js`, the second serverless function after `api/generar-preguntas.js`), chosen over creating accounts by hand in the Supabase dashboard because the user explicitly rejected that ("Realmente, no quiero registrar a mano. Quien tenga la url que se registre") — friends still self-register, they just need a code. The endpoint reads two server-only env vars, `CODIGO_INVITACION` (one or several codes, comma-separated, so a code can be rotated without invalidating the previous one; compared trimmed + case-insensitively, in constant time over a sha256 digest so neither length nor a matching prefix leaks) and `SUPABASE_SERVICE_ROLE_KEY`, validates the code, then creates the account with `supabase.auth.admin.createUser({ email_confirm: true, user_metadata: { username } })`. It also **refuses the `pabloadmin` username outright** — admin is decided by a username match against `ADMIN_NAME` in `App.jsx`, so letting a stranger register that name handed over admin; the real account already exists, so nothing legitimate breaks. Client-side, `handleSignup(username, password, codigo)` no longer calls `supabase.auth.signUp` at all: it POSTs to `/api/registro` and, on success, immediately `signInWithPassword`s (the server-created account has no session), falling back to the pre-existing "Cuenta creada, ya puedes entrar" card if that sign-in fails. `AuthScreen` gained a fourth input ("Código de invitación", signup mode only) prefilled from the URL via the module-level `codigoDelEnlace()` (`?c=` or `?codigo=`), which **also defaults `modo` to `"signup"`** — so one shareable link (`…/?c=CODIGO`) lands straight on the create-account form with the code filled in, and the code never has to be dictated separately. Brute force is capped by `registro_intentos` (`supabase-registro-intentos.sql`): one row per attempt (successful or not), max 8 per IP per hour (`x-forwarded-for`'s first entry), with opportunistic deletion of rows older than 2 days. That table deliberately has **RLS enabled and no policies at all** — only the service_role key (i.e. only `api/registro.js`) reaches it, so the anon key in the bundle can't read it or wipe it to reset the counter. Validating any of this in `App.jsx` would be theatre, since that file ships to every visitor — hence the endpoint. **Still to be done by hand in the Supabase/Vercel dashboards:** set both env vars on Vercel, run `supabase-registro-intentos.sql`, and turn OFF Authentication → Sign In / Providers → Email → "Allow new users to sign up" (the admin API used by the endpoint keeps working regardless; this only closes the direct `signUp` path against the anon key). Until that toggle is off, the old open `signUp` route still exists at the API level even though the UI no longer uses it — the `/signups? not allowed|disabled/` branch of the old error mapping was removed along with the `signUp` call. Deleting a user from Authentication → Users failed with a foreign-key error, fixed by `supabase-borrar-usuario-en-cascada.sql`: the `user_id` columns added by `supabase-vincular-datos-personales.sql`/`supabase-flashcards-privadas.sql`/`supabase-preguntas-progreso.sql` were declared `references auth.users(id)` with no `on delete` clause, so Postgres defaulted to NO ACTION and blocked the delete as soon as a user had any row — which is immediately, since `rachas` gets a row on first login. That migration rebuilds the six FKs (`rachas`, `fallos`, `favoritos`, `flashcards`, `flashcards_progreso`, `preguntas_progreso`) with `on delete cascade`, so deleting an account now takes its streaks, fails, favourites, flashcards and progress with it. It finds the constraints through `pg_constraint` rather than by expected name: a `drop constraint if exists rachas_user_id_fkey` would silently no-op on a differently-named constraint and the new cascading FK would just sit alongside the old restrictive one, leaving the block in place. `duelos`/`duelo_respuestas` are unaffected (keyed by the free-text `name`, no FK), so a deleted user's name survives in old duel rows. **Postgres OR-s permissive policies, and a stray one defeated the whole flashcards privacy model:** `flashcards` stayed visible to every logged-in user long after `supabase-flashcards-privadas.sql` was run, because two extra policies (`flashcards_select` with `qual = true`, and `flashcards_insert`) sat alongside the `*_propio` ones — created separately, most likely from the Supabase dashboard, so the migration's `drop policy if exists "flashcards_select_auth"` never matched them and the `if exists` swallowed it silently. Removed by `supabase-limpiar-politicas-duplicadas.sql`, which also carries the listing query to check the other personal tables. Two things this session established the hard way, worth not relearning: a `drop policy if exists` by expected name proves nothing — list the surviving policies afterwards; and `supabase-flashcards-privadas.sql` had in fact never been run at all until now (found because the cascade migration below failed on a missing `flashcards.user_id`), so a migration file sitting in this repo is NOT evidence that it reached the database.
