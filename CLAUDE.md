# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build
- `npm run preview` — preview a production build locally

There is no lint or test setup in this repo (no test framework, no ESLint config).

## Architecture

This is a small single-page React app ("AUTOPIR", formerly "Ruta PIR"; repo/package name academia-pir), built with Vite, backed by Supabase.

- Entry chain: `index.html` → `src/main.jsx` → `src/App.jsx`. `src/App.jsx` is the entire application (~2000 lines): all components, view logic, and Supabase calls live in this one file, organized as several feature components rendered by a top-level `AcademiaPIR` component based on a `section` state variable (tab navigation).
- Sections/tabs (`section` state, set via the nav in `AcademiaPIR`; only 4 tabs remain, in this order): `simulacros` (self-test quizzes, labeled "Autoevaluaciones" — see below), `duelo` (1v1 duel/battle mode), `flashcards` (spaced-repetition flashcards, Anki-style, front/back cards seeded from an imported Anki deck — see `flashcards`/`flashcards_progreso` below), `perfil` (last tab: fail history, favorites — kept deliberately light; the daily wheel/"ruleta" used to live here but was relocated into the header, see phase 2 below). There is no `temario` tab — `TEMARIO` (static data in `src/temario.js`) is still imported and used internally to ground AI question generation (`GenerarPreguntasIA`), just not shown as a readable tab. There used to be a `curiosidades` tab (AI-generated trivia, via `api/generar-curiosidades.js`); it was replaced outright by `flashcards` per user request — the `curiosidades`/`curiosidades_vistas` tables and `supabase-curiosidades.sql` are dead but left in Supabase/the repo as history, nothing in `App.jsx` references them anymore.
- `banco` (question bank — "Reales" curated + "Inventadas por IA" AI-generated, open to all users with a daily quota, save-to-bank admin-only; no course/subject filter, just a free-text search box that filters the current tab's questions by substring match against the question/options/explanation/tema) and `ranking` (leaderboard + streaks) are **not** nav tabs — like `Logros` (level/badge grid + streak & accuracy stats), they live behind small icon buttons in the header (`Header`'s `mostrarBanco`/`mostrarRanking` state, next to the pre-existing `mostrarLogros`), positioned award-icon (Logros) → trophy-icon (Ranking) → list-icon (Banco) → gear (Ajustes) → logout. Unlike `Logros`'s small anchored dropdown, clicking the Banco or Ranking icon opens a full-screen overlay (`styles.pantallaCompleta`, `position: fixed; inset: 0`, its own close/`X` button up top) rendering the exact same `<BancoPreguntas>`/`<Ranking>` components and props that used to live in the tabbed `<main>` — the components themselves are unchanged, only their entry point moved from a nav tab to a header-triggered overlay. `Header` now needs the question-bank CRUD callbacks and `rachas` passed down from the root alongside its original `user`/`onLogout`/`miRacha`/`onAjustes` props.
- `PreguntaCard` (the expandable question row inside `BancoPreguntas`) no longer reveals the correct option (and the explanation, which usually gives it away) as soon as a question is expanded — a local `mostrarCorrecta` state (reset to `false` every time the card is expanded/collapsed via `toggleOpen`) gates the correct-answer highlight/checkmark and the explanation text behind a "Ver respuesta correcta" button rendered under the options list; pressing it reveals both instantly. This only applies to `PreguntaCard` — the equivalent review UIs in `Simulacros`' post-quiz screen and `MiPerfil`'s fail history still reveal the correct answer immediately, since those are reviewing an already-answered question rather than browsing the raw bank.
- `Simulacros` ("Autoevaluaciones"): the course/subject picker is labeled "Exámenes" and only lists `curso` values that look like an exam edition (matched via the module-level `esExamen(curso)` helper, a `/^pir\b/i` regex — e.g. "PIR 18", "PIR 20", "PIR 21"…"PIR 25"); the near-empty leftover subject-labeled `curso` values (e.g. "Psicopatología") are filtered out of this specific dropdown, though "Todos" still aggregates everything in the current `incluirInventadas`-scoped pool as before. The dropdown's exam options are sorted newest-first by the number in the label (e.g. PIR 26, 25, 24…), not by insertion/appearance order — extracted with a plain `/\d+/` match on the `curso` string. "Modo relámpago" was redesigned from its original fixed 5-question/60-second countdown into an unlimited streak mode: `startRelampago` shuffles every real (non-`inventada`) question across all exam-labeled cursos (`esExamen`) into the pool, questions are answered one at a time (elapsed time just ticks up for display, no time limit), and the round ends the instant an answer is wrong (`"Racha terminada"`) or the moment the whole shuffled pool has been answered correctly (`"¡Racha perfecta!"`) — there's no repeat-of-failures round like the regular mode. Each new relámpago run reshuffles from scratch (no memory of what was seen in past runs, so repeats before exhausting the pool are expected and intended). Only modo relámpago's result is submitted anywhere: `onStreakAnswer` (which drives `rachas.racha_actual`/`racha_record`, shown as the "Autoevaluaciones" columns on the Ranking tab) and `onFinish`/`submitScore` (insert into the `ranking` table — currently otherwise unused for display) are now gated to `relampago === true`; regular course-based autoevaluaciones no longer touch either, to keep that ranking driven by one well-defined game mode. `onProgresoDiario` (weekly league + daily-wheel eligibility) and `onFallo` (fail history in Perfil) are unaffected and still fire for both modes — including relámpago's own failed question, which still lands in Perfil's fail history like any other. A small persistent `rachaViva` counter (reset to 0 in `startRelampago`, incremented on every correct answer while `relampago`) sits top-right of the run header next to the timer, as a `Flame` icon + number; the flame renders dim/grey ("apagada") while `rachaViva <= recordPrevio` (`miRacha.racha_record`, passed down as a prop from the root) and switches to a lit, glowing orange state the moment the live streak exceeds that prior personal record. The post-quiz "Toca una pregunta para repasarla" squares (`styles.cuadroPregunta`) were previously always rendered in the red/`ACENTO` palette regardless of outcome, which per user feedback looked like every question had been failed; they're now colored from `resultados[q.id].correct` (green/`CORRECTO` vs red/`ACENTO`) — in the regular (non-relámpago) mode this renders every square green once the round finishes, since a question only leaves the repeat-of-failures loop once answered correctly, so by the time `state === "done"` every entry in `resultados` is `correct: true` and the grid correctly reflects "you got everything right in the end"; in modo relámpago, which has no repeat round, this instead shows a true mix — green for the questions answered correctly and red for the single wrong answer that ended the streak.
- The `curso` column on `preguntas` is a free-text field, not a fixed taxonomy — for a chunk of imported real questions it actually holds an exam/simulacro label (e.g. "Simulacro 01 (AMIR)") rather than a subject name; those get renamed to their real "PIR YY" edition label via one-off `update` statements in `supabase-*.sql` files as the user requests each renaming (see `supabase-rename-simulacros.sql` for the pattern: a regex anchored on the simulacro number to avoid collisions like "1" matching "10"). Besides renamed simulacros, whole past exams have also been transcribed from PDF and `insert`ed directly with `curso` set to their edition label: `supabase-pir20-preguntas.sql` (198 questions, curso="PIR 20", from an APIR "Simulacro 5" practice-exam PDF; 12 annulled questions from the source were skipped; includes real `explicacion`/`tema` per question) and `supabase-pir18-preguntas.sql` (235 questions, curso="PIR 18", from the official 2018 PIR exam PDF cross-checked against the Ministerio de Sanidad's official answer key; no explanations exist for this source, so `tema` is a placeholder "Pregunta N" and `explicacion` is null), `supabase-pir16-preguntas.sql` (228 questions, curso="PIR 16", same official-exam-PDF-plus-answer-key pattern as PIR 18 — 7 annulled questions, identified by a blank correct-answer cell on the Ministerio's own answer page, were skipped: 23, 25, 27, 46, 69, 74, 102), `supabase-pir15-preguntas.sql` (226 questions, curso="PIR 15", same pattern — 9 annulled questions skipped: 24, 46, 84, 91, 100, 114, 125, 153, 214), and `supabase-pir19-preguntas.sql` (180 questions, curso="PIR 19" — the official exam actually sat in January 2020 under the Ministerio's own cover title "PRUEBAS SELECTIVAS 2019", 175 questions + 10 reserve = 185 numbered, 5 annulled skipped: 35, 69, 114, 134, 185; not to be confused with the already-existing curso="PIR 20", which per above is actually an unrelated APIR practice simulacro, not this official exam — before transcribing this one the user was walked through a content-based check, grepping this repo's other transcribed exam files and searching the live question bank for a distinctive phrase from this PDF, to confirm it wasn't already sitting in the database under a different label like one of the renamed "PIR 21"-"PIR 25" simulacros). All five were run by the user directly in the Supabase SQL editor. `supabase-pir16-preguntas.sql`, `supabase-pir15-preguntas.sql` and `supabase-pir19-preguntas.sql` were each generated (not hand-typed) by a throwaway Node script in the session's scratchpad that built a JS array of `{n, p, o, c}` from the transcribed PDF pages, validated every row before emitting SQL (exactly 4 options, `correcta` in 0-3, no duplicate/missing/annulled question numbers, every `pregunta` ending in `:` or `?`, and — directly per user request after the earlier `. NN`-suffix cleanup — every field checked against the same trailing "period + stray number" regex used in `supabase-detectar-basura-preguntas.sql` so that artifact couldn't be reintroduced), and only wrote the `.sql` file once all checks passed. `supabase-detectar-basura-preguntas.sql`/`supabase-detectar-finales-raros.sql` only look at the END of `pregunta`/`opciones`/`explicacion` text; a distinct artifact — leftover PDF-layout fragments pasted MID-sentence (e.g. "...de tener Pá una discapacidad..." in a PIR 25/"Simulacro" question, an unrelated short capitalized token stuck in the middle) and words merged with no space from a lost line-break (e.g. "sentimientosnegativos") — needed a separate diagnostic, `supabase-detectar-fragmentos-preguntas.sql`: one regex flags a short (1-3 letter) capitalized token surrounded by lowercase words (real domain acronyms like DSM/CIE/PIR/EMDR are always fully uppercase and don't match), another flags any 20+-letter unbroken run of letters as a candidate merged-word. Both are diagnostic-only (like the other `detectar-*` scripts) since, unlike the trailing-garbage case, there's no single safe regex substitution that fixes mid-sentence corruption in bulk — each hit needs eyes-on review and its own targeted fix. `supabase-arreglar-pregunta-disforia-pir25.sql` is one such one-off fix, for the specific PIR 25 "disforia por la integridad corporal" question the user first spotted this in, scoped by `curso` plus a stable substring of the question so it only ever touches that one row; `supabase-arreglar-explicacion-sahos-pir20.sql` fixes a second, unrelated instance found by manually reviewing the diagnostic's results — "apneahipoapnea" missing its separator in a PIR 20 explicación — scoped by exact `id`. After the user asked for the whole ~2102-row table to be checked (not just the rows already spotted by eye) and the Supabase SQL editor turned out to cap displayed results at 100 with no way to raise it, the full table was exported in one shot via a `jsonb_agg(jsonb_build_object(...))` query (packs every row into a single JSON cell, sidestepping the row cap) that the user ran and pasted back as CSV; every hit from both `supabase-detectar-fragmentos-preguntas.sql` queries was then reviewed by hand against that export, with the 20+-letter-run candidates additionally cross-checked with `hunspell` (`es_ES` dictionary) — a word is only treated as two merged words if one of hunspell's suggested corrections, spaces/hyphens stripped, exactly reconstructs the original (this correctly separates real artifacts like "individualismocolectivismo" from legitimate one-word Spanish terms like "electroencefalografía" or "contracondicionamiento", which hunspell either accepts outright or only offers non-matching suggestions for). This turned up two more distinct problems, fixed together in `supabase-arreglar-fragmentos-y-palabras-pegadas.sql` (16 rows, each scoped by exact `id`): the same loose "Pá" PDF-layout fragment from the PIR 25 case above, recurring in 8 more rows across PIR 22-24 (not the isolated incident it first looked like), and 8 rows across PIR 20-24 where a compound term that should carry a hyphen (e.g. "cognitivo-perceptivos", "estabilidad-inestabilidad", "individualismo-colectivismo", "despersonalización-desrealización", "dialéctico-conductual") lost it and got glued into one word during PDF extraction — confirmed in one case by a sibling option in the very same question ("trastorno desafiante-oposicionista" vs. the broken "trastorno desafianteoposicionista" a couple of options down).
- `Flashcards`: front/back cards (`flashcards.frontal`/`.posterior`, grouped by `mazo`) reviewed with a simplified SM-2 spaced-repetition algorithm (`calcularSM2` in `App.jsx`, same model Anki uses) — a card is "due" when `flashcards_progreso.proxima_revision` is null or `<=` today. Each review ends with one of 4 difficulty ratings (Muy difícil/Difícil/Fácil/Muy fácil, mapped to SM-2 quality 0/3/4/5) which updates that user's `ease_factor`, `intervalo_dias`, `repeticiones` and `proxima_revision` for that card via `registrarRepasoFlashcard`. Before starting, the user picks how many due cards to do that round (`numTarjetas`, defaulting to `TAM_SESION_FLASHCARDS` = 20, same raw-while-typing/clamp-on-blur input pattern as `Simulacros`' cantidad field); `ordenarPorPrioridad` then orders the due pool so cards just reset by a "Muy difícil" rating (`repeticiones === 0`) come first, other due reviews next (most overdue first), and never-seen cards last, before slicing to the chosen count — so the ordering itself reacts to the difficulty feedback already given, not just the next-due-date. **Flashcards are private per user, not a shared deck** (changed from the original single shared "Mi baraja" Anki import): `flashcards` has a `user_id` column (`supabase-flashcards-privadas.sql`, run after `supabase-enable-rls.sql`) and RLS restricts select/insert/update/delete to `auth.uid() = user_id`, so the query that fetches `flashcards` (a plain `.select("*")` with no client-side filter, same call as before) now transparently returns only the caller's own cards — nobody sees anyone else's. The original 271-card "Porcentajes/ prevalencias" deck (still loaded once via the bulk `insert` in `supabase-flashcards.sql`) was reassigned to the admin's account by that migration's backfill, so it became Pablo's personal starting deck rather than disappearing; everyone else starts with zero cards. `NuevaFlashcard` (an "Añadir tarjeta" button that expands into a `mazo`/`frontal`/`posterior` form, mirroring `FlashcardEditableCard`'s own edit-form layout) lets anyone add their own cards — shown both on the zero-cards empty state and inside "Ver, añadir y editar tarjetas" — via `onAdd` → `addFlashcard` (`supabase.from("flashcards").insert(...)`; `user_id` fills itself in from the column's `default auth.uid()`, no client-side ownership logic needed). `FlashcardEditableCard` no longer gates editing behind `user.isAdmin` (ownership itself is now the gate, enforced server-side by RLS) and gained a "Borrar" button with an inline "¿Seguro? Borrar" confirm step, wired to `onDelete` → `deleteFlashcard` (`supabase.from("flashcards").delete(...)`, also clears any matching `flashcards_progreso` row locally). The `mazo` field is now a free-text label the card's owner picks per card (defaults to "General" if left blank on add) rather than a single deck name shared by the whole table — `Flashcards`' header subtitle no longer reads `flashcards[0].mazo` (which broke once a user's deck could be empty or span several self-chosen mazo names), just a card count. **Folders, and folders-of-mazos (file-browser redesign):** the original flat pill-chip row of `mazo` names (`styles.chipCarpeta`) was replaced, per user request for something closer to a real deck-browser app (reference screenshot: a vertical list of folder rows, each with an icon, a card count, and a due-count badge, expandable into the mazos inside), with a two-level file-browser UI, still with **zero schema change** — a `mazo` value containing "/" (e.g. `"Troncales/Neuroanatomía"`) is read as living inside the folder named by the part before the slash, alongside any sibling mazos under that same prefix; a `mazo` with no "/" is simultaneously its own folder and its own mazo (a flat leaf row, no folder icon — matches "Básica" in the reference screenshot having no folder). `arbolCarpetas` (a `useMemo` in `Flashcards`) groups the distinct `mazo` values this way into `{ nombre, esCarpeta, tieneBase, hijos }` entries (`esCarpeta` true only if at least one sibling mazo shares that folder prefix; `tieneBase` covers the rare case of a user having cards directly in `"Troncales"` *as well as* in `"Troncales/Algo"`, surfaced as a "General" row inside the folder). `statsPorMazo`/`statsDeCarpeta` precompute per-mazo and per-folder (prefix-matched, so a folder aggregates all its mazos) card counts, due-today counts and most-recent `created_at`, feeding the badge shown on each row (`"N hoy"` in the folder-row badge when that mazo/folder has cards due). Three pieces of navigation state drive it: `mostrandoLista` (browsing the folder tree vs. the review/edit view for a selection), `carpetaNavegando` (which folder is currently open, showing its mazos), and the existing `mazoActivo` plus a new `filtroCarpeta` (an aggregate "all mazos in this folder" selection, prefix-matched) — picking either sets `mostrandoLista` to false and reuses the exact same `flashcardsDeCarpeta`/`pendientes`/"Ver, añadir y editar tarjetas" review UI that already existed, just reached via this browser instead of the old chip row; a "← Carpetas" link takes you back to wherever you were browsing (root list or inside a folder) without losing your place. This browser is now always the landing view (`mostrandoLista` starts `true` on every mount), even for a user with only one `mazo` — initially it only rendered when there was more than one distinct `mazo`, defaulting straight to the review view otherwise, but per explicit user feedback ("no quiero que se vea así [el panel de repaso] lo de abajo, quiero que salgan los iconos de las carpetas según las que haya y lo de arriba salga una vez que has abierto una carpeta y seleccionado un mazo") the review/edit panel ("Tienes N tarjetas para repasar hoy" + "Empezar repaso" + "Ver, añadir y editar tarjetas") never appears until a folder or mazo has actually been picked, regardless of how many exist — a user with a single mazo still sees it as one row (folder or flat leaf, per the usual rule) they have to click through, same as anyone else. A child mazo's displayed label (`m.slice(carpeta.nombre.length + 1)`) is `.trim()`-ed for display only (not the underlying `mazo` value used for filtering) since the admin's original seeded deck is literally named `"Porcentajes/ prevalencias"` (a space after the slash, predating this folder convention and coincidentally readable as one) — without the trim its row would show a leading space in the label. `SelectorCarpeta` (shared by `NuevaFlashcard` and `ImportarFlashcards`, used when adding/importing cards) is unchanged in mechanics — still a `<select>` of existing mazo names plus a "+ Nueva carpeta..." free-text option — except its placeholder now documents the "/" convention so users know how to file a new mazo inside a folder, and it gained an optional `forzarNueva` prop (threaded through `NuevaFlashcard`/`ImportarFlashcards`) that starts it straight in free-text mode instead of the `<select>`, used only by the two new creation entry points below.

**Full CRUD on carpetas/mazos from the browser itself:** per direct user request ("ahora desde aquí deja añadir más carpetas y cambiar el nombre a cada carpeta o eliminar incluso, y dentro de las carpetas se pueda añadir varios mazos o el que esté ya se pueda editar"), the folder-browser screens gained create/rename/delete controls, still with zero schema change — everything is still bulk `update`/`delete` on the `flashcards.mazo` free-text column:
- **Crear**: both the root list and an opened folder now render `<NuevaFlashcard>`/`<ImportarFlashcards>` inline below the rows (`forzarNueva` on, so the free-text field shows immediately instead of a dropdown) — at root with a blank `mazoPorDefecto` (type any name, with or without "/" to make it a folder), inside a folder pre-filled with `"<carpeta>/"` so the user only has to type the mazo's own name after the slash.
- **Renombrar/Borrar**: `FilaCarpetaEditable` (a variant of `FilaNavegacion` used everywhere except the synthetic "Todas..." rows) adds a pencil and trash icon per row; the pencil swaps the row for an inline text input + Guardar/Cancelar, the trash swaps it for an inline "¿Seguro? Borrar" confirmation — both local `useState` inside the row itself, no lifted "which row is editing" state needed. Both actions bottom out in two new root-level handlers, `renombrarMazo(viejo, nuevo, cascada)`/`eliminarMazo(nombre, cascada)` (passed down as `onRenombrarMazo`/`onEliminarMazo`), which operate on the already-loaded `flashcards` client state rather than a fresh query — `cascada` is the key distinction: `true` for a folder row (renaming/deleting it cascades to everything under `"nombre/"` too, preserving each child's own suffix on rename) and `false` for a single mazo/leaf row or the "General" pseudo-row inside a folder (exact-match only, so it can't collide with its siblings). Rename groups affected cards by their *computed new* `mazo` value (since different children get different new values in a cascade) and issues one `update(...).in("id", ids)` per group; delete is one `delete().in("id", ids)`, also clearing matching `flashcards_progreso` rows — same pattern `deleteFlashcard` already used per-card. A `useEffect` watches `carpetaNavegando`: if the folder you're browsing stops existing in `arbolCarpetas` (you renamed or fully emptied it), it bounces you back to the root list instead of showing a dead end. The "General" row's rename input is pre-seeded with the real underlying value (`carpeta.nombre`, via a `valorEditable` prop separate from its display `titulo`) rather than the literal word "General", so clicking Guardar without editing correctly no-ops instead of renaming the mazo to the string "General"; a hijo row's rename input is pre-seeded with just its short suffix (not the full `"carpeta/hijo"` path) and the carpeta prefix is silently re-added on save. `ImportarFlashcards` (a second button next to "Añadir tarjeta", same collapsed-button-that-expands-into-a-`Card` pattern) is a bulk-import textarea: paste one card per line as `frontal<sep>posterior`, separator auto-detected per line (tab, then `" | "`, then `;`, in that priority order — tab first since that's what pasting from a spreadsheet produces) and shown live as a "N tarjetas detectadas" count before submitting; wired to `onAddBulk` → `addFlashcardsBulk` in the root component, a single multi-row `supabase.from("flashcards").insert([...])` (not one request per card).
- Auth is real: Supabase Auth (email+password), using a synthesized fake email `username@ruta-pir.local` since Supabase Auth requires an email-shaped identifier — see `emailDeUsuario`/`usuarioFromSession`/`handleLogin`/`handleSignup` in `App.jsx`. Supabase's Auth dashboard must have "Confirm email" disabled for the Email provider (no real inbox exists for the fake domain, so signup must grant a session immediately). Admin access is still gated by a hardcoded username check against `ADMIN_NAME` ("pabloadmin") — whoever registers that exact username becomes admin and is displayed/stored everywhere as `name: "Pablo"`.
- Backend is Supabase (`src/supabaseClient.js`), used directly from `App.jsx` via `supabase.from(...)` calls, and from `api/generar-preguntas.js` (a separate server-side client, same anon key) to enforce the daily AI-question quota. Tables in use: `preguntas` (questions), `ranking`, `rachas` (streaks + daily-progress + badge totals), `duelos`/`duelo_respuestas` (duel state/answers), `fallos` (per-user per-question fail counts), `favoritos` (per-user saved questions), `ia_uso` (per-user per-day AI generation quota), `flashcards` (shared flashcard deck content), `flashcards_progreso` (per-user SM-2 review state per card). There is no schema/migrations folder in this repo — the schema lives only in Supabase itself; one-off `supabase-*.sql` files at the repo root are migrations already handed to and run by the user, kept only as a record.
- UI preferences (font-size "zoom" scale, page background color, and — as of the visual redesign below — a typography choice, all set from the gear icon in the header) are per-device, persisted to `localStorage` under `pir-ajustes` — not synced through Supabase.
- **Visual redesign, phase 1 ("cuaderno de examen"):** the app is mid-migration from its original navy/teal SaaS look to a new editorial identity worked out first as standalone HTML mockups (Artifacts, not part of this repo) before being ported into `App.jsx`. Design tokens live as top-level `const`s right above `AJUSTES_DEFECTO` (`TINTA`/`TINTA_SUAVE`/`TINTA_TENUE` ink, `RAYA`/`RAYA_FUERTE` hairline borders, `ACENTO`/`ACENTO_SUAVE` — a brick red, the brand/chrome/wrong-answer color, replacing the old teal `#2E7D6B` for anything that isn't a correctness signal, `CORRECTO`/`CORRECTO_SUAVE` — green, reserved strictly for correct-answer/success states, `ORO` for streak/badge accents) plus `SOMBRA_SUAVE` (shared card shadow) declared just above the `styles` object. Display typography (Fraunces by default) is threaded through via a CSS custom property, not props: the root app `<div>` sets `"--font-display"` inline from `ajustes.fuente`/`FUENTES`, and every serif/heading spot in `styles` (and a few inline JSX styles) reads `fontFamily: "var(--font-display)"` so switching fonts in Ajustes re-themes the whole tree with no prop drilling. `FUENTES` (Fraunces / Source Serif 4 "Clásica" / IBM Plex Sans "Solo sans") is a new `AjustesPanel` control alongside the existing size/color ones, stored as `ajustes.fuente`. `COLORES_FONDO` was reworked to the new light paper tones (dark/near-black tones were deliberately left out of this simple flat-background-swap mechanism, since ink colors don't flip with it). ### Things to be aware of

- `src/supabaseClient.js` has the Supabase URL and anon key hardcoded inline rather than read from environment variables.
- The Vite config file was originally named `Vite.config.js` (capital `V`), which Vite's default config auto-discovery (lowercase `vite.config.*`) silently ignored — confirmed via `DEBUG=vite:config`, which reported "no config file found" and fell back to zero-config defaults (no `@vitejs/plugin-react`, so no Fast Refresh in `npm run dev`). Renamed to lowercase `vite.config.js`; the react plugin is now actually active.
- `className="animate-spin"` (used on `Loader2` in several places — the root loading screen, `AuthScreen`'s submit button, `GenerarPreguntasIA`'s "Generar" button, and `Duelo`'s "Esperando a un oponente...") never actually spun: there's no Tailwind in this project and no CSS file ever defined an `.animate-spin` keyframe, so the class was applied but inert since the feature was first written (confirmed against the oldest commit of `App.jsx` in the repo — it never worked, this isn't a regression from any later change). Found while investigating a user report that "la animación del duelo al empezar no sale" (turned out to mean this spinner, not the static `Swords` icon nearby, which has never had any animation of its own in any revision of the file). Fixed with a small global `<style>` block in `index.html` (`@keyframes animateSpin` + `.animate-spin { animation: animateSpin 1s linear infinite; }`) rather than per-component, since the class is shared across unrelated components.
- `public/` holds static PWA assets so the app can be "added to home screen": `manifest.webmanifest` (name/short_name "AUTOPIR", `theme_color`/`background_color` `#1C170F` to match the login screen's dark card, `display: "standalone"`) plus `icon-192.png`/`icon-512.png`/`apple-touch-icon.png` — a simple gold "A" monogram (`Big Shoulders Display`, weight 900, on the `#1C170F`/`#E9C878` portada palette) rendered via a one-off Playwright screenshot (no image-generation tool available), not hand-drawn. `index.html` links the manifest, the apple/PNG icons, and a `theme-color` meta. Deliberately no service worker/offline caching — this is just an install/shortcut icon for a small private group, not a full offline-first PWA.
- **Security hardening for sharing with a small group:** `supabase-enable-rls.sql` (one-off, run by the user in the Supabase SQL editor like the other `supabase-*.sql` files) enables Row Level Security on all 10 tables and requires an authenticated Supabase session for virtually every read/write — before this, the client-exposed anon key alone allowed full read/write/delete on every table with no login at all. `preguntas`/`flashcards` writes (insert/update/delete on `preguntas`, update on `flashcards`) are further restricted to the admin's synthesized email (`auth.email() = 'pabloadmin@ruta-pir.local'`), mirroring the existing client-side `isAdmin` gating but now enforced server-side too. `ia_uso` is the one exception left open to the `anon` role: it's only ever touched by `api/generar-preguntas.js`, a serverless function that creates its own Supabase client from the anon key without forwarding the caller's session, so it always acts as `anon`, never `authenticated`. What RLS does **not** cover: no table has a `user_id`/`auth.uid()` column, so rows are all keyed by the free-text `name` field — an authenticated user could in principle read/write another user's `rachas`/`fallos`/`favoritos` row by calling the REST API directly (not through the UI). Fixing that fully needs a schema change (a `user_id` column plus rewritten policies and client queries), judged out of scope for now given the small trusted audience — **since closed** by `supabase-vincular-datos-personales.sql` (run after `supabase-enable-rls.sql`): adds a `user_id uuid references auth.users(id) default auth.uid()` column to `rachas`/`fallos`/`favoritos`/`flashcards_progreso`, backfills it for existing rows by matching `name` against `auth.users.raw_user_meta_data->>'username'` (case-insensitively, with a special-cased `name = 'Pablo'` → username `pabloadmin` since the admin's display name and login username differ), then replaces the earlier `*_auth` policies with `auth.uid() = user_id` checks on insert/update/delete (and on select too for `fallos`/`favoritos`/`flashcards_progreso`, which are purely personal with no shared display) — `rachas` keeps open select since Ranking/Logros show everyone's streaks. No client code changes were needed: `user_id` populates itself via the column `default` on insert, and upserts' `ON CONFLICT DO UPDATE` never touches it after that. Deliberately left out: `duelos`/`duelo_respuestas` (shared state between two named players, doesn't fit a single `user_id` owner column without a larger redesign) and `ranking`/`preguntas`/`flashcards` (already correctly shared/admin-gated, no change needed). `supabase-comprobar-admin.sql` is a read-only check for whether anyone besides the intended admin has registered under (or near) the `pabloadmin` username/email. Enabling RLS required a companion code fix first: the effect that loads `preguntas`/`ranking`/`rachas`/`flashcards` (in the root `AcademiaPIR` component) used to run exactly once on mount, before any login, so under RLS a first-time login/signup in a fresh browser would see those go empty and never recover without a manual refresh; the effect now tracks whether a session existed at that initial load and, if the auth state later transitions from no-session to a session (a fresh login/signup), re-runs the same fetch once now that the client is authenticated. Real signup is still wide open (no invite gate) — anyone who finds the app's URL can self-register and use it fully (short of admin features) via `handleSignup`; there is no code-level fix for this yet, since a real gate needs either disabling public sign-ups in the Supabase Auth dashboard between invites or a server-side invite check, neither of which has been done as of this writing.
