# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- `npm run dev` — start the Vite dev server
- `npm run build` — production build
- `npm run preview` — preview a production build locally

There is no lint or test setup in this repo (no test framework, no ESLint config).

## Architecture

This is a small single-page React app ("AUTOPIR", formerly "Ruta PIR"; repo/package name academia-pir), built with Vite, backed by Supabase.

- Entry chain: `index.html` → `src/main.jsx` → `src/App.jsx`. `src/App.jsx` is the entire application (~2000 lines): all components, view logic, and Supabase calls live in this one file, organized as several feature components rendered by a top-level `AcademiaPIR` component based on a `section` state variable (tab navigation).
- Sections/tabs (`section` state, set via the nav in `AcademiaPIR`; only 4 tabs remain, in this order): `simulacros` (self-test quizzes, labeled "Autoevaluaciones" — see below), `duelo` (1v1 duel/battle mode), `flashcards` (spaced-repetition flashcards, Anki-style, front/back cards seeded from an imported Anki deck — see `flashcards`/`flashcards_progreso` below), `perfil` (last tab: fail history, favorites — kept deliberately light; the daily wheel/"ruleta" used to live here but was relocated into the header, see phase 2 below). There is no `temario` tab — `TEMARIO` (static data in `src/temario.js`) is still imported and used internally to ground AI question generation (`GenerarPreguntasIA`), just not shown as a readable tab. There used to be a `curiosidades` tab (AI-generated trivia, via `api/generar-curiosidades.js`); it was replaced outright by `flashcards` per user request — the `curiosidades`/`curiosidades_vistas` tables and `supabase-curiosidades.sql` are dead but left in Supabase/the repo as history, nothing in `App.jsx` references them anymore.
- `banco` (question bank — "Reales" curated real-exam questions + a "Pendientes" tab of real questions not yet attempted, see the per-question progress bullet below; no course/subject filter, just a free-text search box that filters the current tab's questions by substring match against the question/options/explanation/tema) and `ranking` (leaderboard + streaks) are **not** nav tabs — like `Logros` (level/badge grid + streak & accuracy stats), they live behind small icon buttons in the header (`Header`'s `mostrarBanco`/`mostrarRanking` state, next to the pre-existing `mostrarLogros`), positioned award-icon (Logros) → trophy-icon (Ranking) → list-icon (Banco) → gear (Ajustes) → logout. Unlike `Logros`'s small anchored dropdown, clicking the Banco or Ranking icon opens a full-screen overlay (`styles.pantallaCompleta`, `position: fixed; inset: 0`, its own close/`X` button up top) rendering the exact same `<BancoPreguntas>`/`<Ranking>` components and props that used to live in the tabbed `<main>` — the components themselves are unchanged, only their entry point moved from a nav tab to a header-triggered overlay. `Header` now needs the question-bank CRUD callbacks and `rachas` passed down from the root alongside its original `user`/`onLogout`/`miRacha`/`onAjustes` props.
- **Per-question progress tracking, and the "Inventadas por IA" tab's repurposing into "Pendientes":** per user request ("para que tenga un control de que he realizado todas"), a new `preguntas_progreso` table (`supabase-preguntas-progreso.sql`, same `name`+`user_id`+RLS shape as `fallos`/`favoritos`, one row per user per question: `veces` = total times answered, `acertada` = whether any attempt was ever correct) is written to from a new root handler, `registrarProgresoPregunta(pregunta, correcta)` (upserts by `name`+`pregunta_id`, incrementing `veces` and OR-ing `acertada`), wired into both `Simulacros` (`onRespuestaPregunta`, called in `elegir` alongside `onFallo`/`onProgresoDiario`, same `ronda === 1` first-attempt-only gate so repeat-round re-answers of previously-failed questions don't double-count) and `Duelo` (`onRespuestaPregunta`, called in `responder` alongside `onProgresoDiario`) — so a question's count reflects attempts from either mode. `BancoPreguntas` reads this via a new `preguntasProgreso` prop (root → `Header` → `BancoPreguntas`) and: (1) shows a `ProgresoPreguntaBadge` (an `Eye` icon + the raw `veces` count, gray at 0/tinta once attempted/`CORRECTO`-green once ever correct, with a title tooltip spelling out the count) on every `PreguntaCard`, top-right next to the existing favorito star, so scrolling the list shows at a glance which questions are done; (2) the `SectionTitle` subtitle shows an aggregate `hechasReales/totalReales` count of real questions ever answered correctly (dynamic, not a hardcoded "2102"). The second tab — previously "Inventadas por IA" (`GenerarPreguntasIA` embedded inline, plus any already-saved AI-generated questions) — was replaced outright with "Pendientes ({count})" (`Eye` icon), listing real questions with no progress row or `veces === 0` (attempted-but-never-correct questions are deliberately excluded from both "pendientes" and the "hechas" count — they sit in "Reales" only, neither bucket, until answered correctly at least once); `GenerarPreguntasIA` itself is left defined but unreferenced (Rollup tree-shakes it out of the build), same "dead code left behind, not deleted" precedent as `curiosidades` — any already-saved `inventada` questions are no longer reachable from this screen as a result, which hasn't been raised as a problem but is worth knowing if it ever comes up.
- `PreguntaCard` (the expandable question row inside `BancoPreguntas`) no longer reveals the correct option (and the explanation, which usually gives it away) as soon as a question is expanded — a local `mostrarCorrecta` state (reset to `false` every time the card is expanded/collapsed via `toggleOpen`) gates the correct-answer highlight/checkmark and the explanation text behind a "Ver respuesta correcta" button rendered under the options list; pressing it reveals both instantly. This only applies to `PreguntaCard` — the equivalent review UIs in `Simulacros`' post-quiz screen and `MiPerfil`'s fail history still reveal the correct answer immediately, since those are reviewing an already-answered question rather than browsing the raw bank.
- `Simulacros` ("Autoevaluaciones"): the course/subject picker is labeled "Exámenes" and only lists `curso` values that look like an exam edition (matched via the module-level `esExamen(curso)` helper, a `/^pir\b/i` regex — e.g. "PIR 18", "PIR 20", "PIR 21"…"PIR 25"); the near-empty leftover subject-labeled `curso` values (e.g. "Psicopatología") are filtered out of this specific dropdown, though "Todos" still aggregates everything in the current `incluirInventadas`-scoped pool as before. The dropdown's exam options are sorted newest-first by the number in the label (e.g. PIR 26, 25, 24…), not by insertion/appearance order — extracted with a plain `/\d+/` match on the `curso` string. "Modo relámpago" was redesigned from its original fixed 5-question/60-second countdown into an unlimited streak mode: `startRelampago` shuffles every real (non-`inventada`) question across all exam-labeled cursos (`esExamen`) into the pool, questions are answered one at a time (elapsed time just ticks up for display, no time limit), and the round ends the instant an answer is wrong (`"Racha terminada"`) or the moment the whole shuffled pool has been answered correctly (`"¡Racha perfecta!"`) — there's no repeat-of-failures round like the regular mode. Each new relámpago run reshuffles from scratch (no memory of what was seen in past runs, so repeats before exhausting the pool are expected and intended). Only modo relámpago's result is submitted anywhere: `onStreakAnswer` (which drives `rachas.racha_actual`/`racha_record`, shown as the "Autoevaluaciones" columns on the Ranking tab) and `onFinish`/`submitScore` (insert into the `ranking` table — currently otherwise unused for display) are now gated to `relampago === true`; regular course-based autoevaluaciones no longer touch either, to keep that ranking driven by one well-defined game mode. `onProgresoDiario` (weekly league + daily-wheel eligibility) and `onFallo` (fail history in Perfil) are unaffected and still fire for both modes — including relámpago's own failed question, which still lands in Perfil's fail history like any other. A small persistent `rachaViva` counter (reset to 0 in `startRelampago`, incremented on every correct answer while `relampago`) sits top-right of the run header next to the timer, as a `Flame` icon + number; the flame renders dim/grey ("apagada") while `rachaViva <= recordPrevio` and switches to a lit, glowing orange state the moment the live streak exceeds that prior personal record. `recordPrevio` is **frozen at the start of the run** (a `useState` set in `startRelampago` from `miRacha.racha_record`), not read live from the prop — reading it live meant the flame never lit at all, since `registrarAcierto` raises `racha_record` to `max(récord, racha actual)` on every correct answer, so by the instant `rachaViva` passed the old record the record had already climbed to match it and `rachaViva > recordPrevio` was never true. The post-quiz "Toca una pregunta para repasarla" squares (`styles.cuadroPregunta`) were previously always rendered in the red/`ACENTO` palette regardless of outcome, which per user feedback looked like every question had been failed; they're now colored from `resultados[q.id].correct` (green/`CORRECTO` vs red/`ACENTO`) — in the regular (non-relámpago) mode this renders every square green once the round finishes, since a question only leaves the repeat-of-failures loop once answered correctly, so by the time `state === "done"` every entry in `resultados` is `correct: true` and the grid correctly reflects "you got everything right in the end"; in modo relámpago, which has no repeat round, this instead shows a true mix — green for the questions answered correctly and red for the single wrong answer that ended the streak.
- The `curso` column on `preguntas` is a free-text field, not a fixed taxonomy — for a chunk of imported real questions it actually holds an exam/simulacro label (e.g. "Simulacro 01 (AMIR)") rather than a subject name; those get renamed to their real "PIR YY" edition label via one-off `update` statements in `supabase-*.sql` files as the user requests each renaming (see `supabase-rename-simulacros.sql` for the pattern: a regex anchored on the simulacro number to avoid collisions like "1" matching "10"). Besides renamed simulacros, whole past exams have also been transcribed from PDF and `insert`ed directly with `curso` set to their edition label: `supabase-pir20-preguntas.sql` (198 questions, curso="PIR 20", from an APIR "Simulacro 5" practice-exam PDF; 12 annulled questions from the source were skipped; includes real `explicacion`/`tema` per question) and `supabase-pir18-preguntas.sql` (235 questions, curso="PIR 18", from the official 2018 PIR exam PDF cross-checked against the Ministerio de Sanidad's official answer key; no explanations exist for this source, so `tema` is a placeholder "Pregunta N" and `explicacion` is null), `supabase-pir16-preguntas.sql` (228 questions, curso="PIR 16", same official-exam-PDF-plus-answer-key pattern as PIR 18 — 7 annulled questions, identified by a blank correct-answer cell on the Ministerio's own answer page, were skipped: 23, 25, 27, 46, 69, 74, 102), `supabase-pir15-preguntas.sql` (226 questions, curso="PIR 15", same pattern — 9 annulled questions skipped: 24, 46, 84, 91, 100, 114, 125, 153, 214), and `supabase-pir19-preguntas.sql` (180 questions, curso="PIR 19" — the official exam actually sat in January 2020 under the Ministerio's own cover title "PRUEBAS SELECTIVAS 2019", 175 questions + 10 reserve = 185 numbered, 5 annulled skipped: 35, 69, 114, 134, 185; not to be confused with the already-existing curso="PIR 20", which per above is actually an unrelated APIR practice simulacro, not this official exam — before transcribing this one the user was walked through a content-based check, grepping this repo's other transcribed exam files and searching the live question bank for a distinctive phrase from this PDF, to confirm it wasn't already sitting in the database under a different label like one of the renamed "PIR 21"-"PIR 25" simulacros). All five were run by the user directly in the Supabase SQL editor. `supabase-pir16-preguntas.sql`, `supabase-pir15-preguntas.sql` and `supabase-pir19-preguntas.sql` were each generated (not hand-typed) by a throwaway Node script in the session's scratchpad that built a JS array of `{n, p, o, c}` from the transcribed PDF pages, validated every row before emitting SQL (exactly 4 options, `correcta` in 0-3, no duplicate/missing/annulled question numbers, every `pregunta` ending in `:` or `?`, and — directly per user request after the earlier `. NN`-suffix cleanup — every field checked against the same trailing "period + stray number" regex used in `supabase-detectar-basura-preguntas.sql` so that artifact couldn't be reintroduced), and only wrote the `.sql` file once all checks passed. `supabase-detectar-basura-preguntas.sql`/`supabase-detectar-finales-raros.sql` only look at the END of `pregunta`/`opciones`/`explicacion` text; a distinct artifact — leftover PDF-layout fragments pasted MID-sentence (e.g. "...de tener Pá una discapacidad..." in a PIR 25/"Simulacro" question, an unrelated short capitalized token stuck in the middle) and words merged with no space from a lost line-break (e.g. "sentimientosnegativos") — needed a separate diagnostic, `supabase-detectar-fragmentos-preguntas.sql`: one regex flags a short (1-3 letter) capitalized token surrounded by lowercase words (real domain acronyms like DSM/CIE/PIR/EMDR are always fully uppercase and don't match), another flags any 20+-letter unbroken run of letters as a candidate merged-word. Both are diagnostic-only (like the other `detectar-*` scripts) since, unlike the trailing-garbage case, there's no single safe regex substitution that fixes mid-sentence corruption in bulk — each hit needs eyes-on review and its own targeted fix. `supabase-arreglar-pregunta-disforia-pir25.sql` is one such one-off fix, for the specific PIR 25 "disforia por la integridad corporal" question the user first spotted this in, scoped by `curso` plus a stable substring of the question so it only ever touches that one row; `supabase-arreglar-explicacion-sahos-pir20.sql` fixes a second, unrelated instance found by manually reviewing the diagnostic's results — "apneahipoapnea" missing its separator in a PIR 20 explicación — scoped by exact `id`. After the user asked for the whole ~2102-row table to be checked (not just the rows already spotted by eye) and the Supabase SQL editor turned out to cap displayed results at 100 with no way to raise it, the full table was exported in one shot via a `jsonb_agg(jsonb_build_object(...))` query (packs every row into a single JSON cell, sidestepping the row cap) that the user ran and pasted back as CSV; every hit from both `supabase-detectar-fragmentos-preguntas.sql` queries was then reviewed by hand against that export, with the 20+-letter-run candidates additionally cross-checked with `hunspell` (`es_ES` dictionary) — a word is only treated as two merged words if one of hunspell's suggested corrections, spaces/hyphens stripped, exactly reconstructs the original (this correctly separates real artifacts like "individualismocolectivismo" from legitimate one-word Spanish terms like "electroencefalografía" or "contracondicionamiento", which hunspell either accepts outright or only offers non-matching suggestions for). This turned up two more distinct problems, fixed together in `supabase-arreglar-fragmentos-y-palabras-pegadas.sql` (16 rows, each scoped by exact `id`): the same loose "Pá" PDF-layout fragment from the PIR 25 case above, recurring in 8 more rows across PIR 22-24 (not the isolated incident it first looked like), and 8 rows across PIR 20-24 where a compound term that should carry a hyphen (e.g. "cognitivo-perceptivos", "estabilidad-inestabilidad", "individualismo-colectivismo", "despersonalización-desrealización", "dialéctico-conductual") lost it and got glued into one word during PDF extraction — confirmed in one case by a sibling option in the very same question ("trastorno desafiante-oposicionista" vs. the broken "trastorno desafianteoposicionista" a couple of options down). A third, opposite-direction artifact was later spotted by the user directly in the app (a screenshot): a real word broken apart by a stray internal space, e.g. "está dirigi do a medir" instead of "está dirigido a medir" (PIR 22, Pregunta 125) — fixed in `supabase-arreglar-dirigido-pir22.sql`, scoped by exact `id`. Checking for more instances of this pattern reused the cached full-table export (`preguntas.json` in the session scratchpad, from the earlier `jsonb_agg` pull) rather than asking for a fresh one, since the only rows changed since that export were the already-known 16 from `supabase-arreglar-fragmentos-y-palabras-pegadas.sql`, unrelated to this new pattern: every adjacent word pair in `pregunta`/`opciones`/`explicacion` separated by exactly one space (i.e., no other punctuation between them, to avoid pairing across sentence boundaries) was concatenated and checked against `hunspell` — a pair is only a real candidate if the concatenation comes back as a genuine dictionary word (`*`/`+`/`-` in hunspell's output), the same precision bar used for the merged-word direction, just applied to word *pairs* instead of single long tokens — but this direction turned out far noisier on its own (~52,600 unique adjacent-pairs from the whole bank, 745 of which concatenate to a real word) because so many ordinary two-word phrases coincidentally spell some unrelated dictionary word when squashed together (e.g. "Coping Cat es un tratamiento" → "Cates", or "post hoc es que" → "hoces" — both grammatically normal sentences, not artifacts); the fix was a second hunspell pass checking each half of the pair *on its own*, and only keeping a candidate when at least one half is NOT independently a valid word (a genuine split artifact always leaves one side as a non-word fragment, e.g. "evalua"/"informa"/"pre"/"o" in the hits below, whereas "Cat"/"cat"/"hoc" all check out as valid on their own even standalone) — this cut 745 candidates down to exactly 4 real ones, fixed in `supabase-arreglar-palabras-partidas.sql` (each scoped by exact `id`, one of them touching both `pregunta` and an `opcion` in the same row): "evalua ción" → "evaluación" and "informa ción" → "información" (PIR 22), "pre viamente" → "previamente" (PIR 22, same row as "informa ción"), and "respuesta o perante" → "respuesta operante" (PIR 21, confirmed by two sibling options in the same question that already spell "operante" correctly).
- **"Dónde fallas" (`DondeFallas` en `MiPerfil`, arriba del historial de fallos).** El % de acierto por examen (`curso`) y por tema (`tema`), para saber qué repasar. No necesitó nada nuevo en Supabase: sale de cruzar dos tablas que ya se escribían pero que no se enseñaban juntas en ningún sitio — `preguntas_progreso.veces` (intentos por pregunta) menos `fallos.veces` (fallos por pregunta) son los aciertos, y `agruparAciertos` los suma por la clave que se le pase. Se ordena de peor a mejor, que es el orden en el que conviene repasar. Decisiones que conviene no deshacer sin motivo: (1) lo que no has empezado queda fuera del ranking con `pct: null` en vez de contar como 0%, porque es ausencia de dato, no un mal resultado; (2) por tema se descartan los `Pregunta N` (`TEMA_PLACEHOLDER`), ya que los exámenes oficiales transcritos del PDF no traían tema y si no ensuciarían la lista entera, y se corta en `MAX_FILAS_TEMA` = 15; (3) la barra ya codifica la magnitud, así que el color solo marca lo flojo (<60%, `ACENTO`) en lugar de repintar un degradado de 4 tonos sobre lo que la longitud ya dice, y el número va en tinta, nunca en el color de la barra — todos los recuentos están escritos, así que nada depende del color ni del hover. El pie advierte de la limitación heredada del backfill: lo acertado antes de que existiera `preguntas_progreso` no dejó rastro (solo se guardaban los fallos) y figura como no empezado, y las filas recuperadas de `fallos` arrancan con intentos = fallos, o sea 0%, que es justo lo que consta de ellas.
- `Flashcards`: front/back cards (`flashcards.frontal`/`.posterior`, grouped by `mazo`) reviewed with a simplified SM-2 spaced-repetition algorithm (`calcularSM2` in `App.jsx`, same model Anki uses) — a card is "due" when `flashcards_progreso.proxima_revision` is null or `<=` today. Each review ends with one of 4 difficulty ratings (Muy difícil/Difícil/Fácil/Muy fácil, mapped to SM-2 quality 0/3/4/5) which updates that user's `ease_factor`, `intervalo_dias`, `repeticiones` and `proxima_revision` for that card via `registrarRepasoFlashcard`. Before starting, the user picks how many due cards to do that round (`numTarjetas`, defaulting to `TAM_SESION_FLASHCARDS` = 20, same raw-while-typing/clamp-on-blur input pattern as `Simulacros`' cantidad field); `ordenarPorPrioridad` then orders the due pool so cards just reset by a "Muy difícil" rating (`repeticiones === 0`) come first, other due reviews next (most overdue first), and never-seen cards last, before slicing to the chosen count — so the ordering itself reacts to the difficulty feedback already given, not just the next-due-date. **Flashcards are private per user, not a shared deck** (changed from the original single shared "Mi baraja" Anki import): `flashcards` has a `user_id` column (`supabase-flashcards-privadas.sql`, run after `supabase-enable-rls.sql`) and RLS restricts select/insert/update/delete to `auth.uid() = user_id`, so the query that fetches `flashcards` (a plain `.select("*")` with no client-side filter, same call as before) now transparently returns only the caller's own cards — nobody sees anyone else's. The original 271-card "Porcentajes/ prevalencias" deck (still loaded once via the bulk `insert` in `supabase-flashcards.sql`) was reassigned to the admin's account by that migration's backfill, so it became Pablo's personal starting deck rather than disappearing; everyone else starts with zero cards. `FlashcardEditableCard` no longer gates editing behind `user.isAdmin` (ownership itself is now the gate, enforced server-side by RLS) and has a "Borrar" button with an inline "¿Seguro? Borrar" confirm step, wired to `onDelete` → `deleteFlashcard`. The `mazo` field is a free-text label the card's owner picks per card (defaults to "General" if left blank) rather than a single deck name shared by the whole table.
- **Mazos are flat, one level, no nesting — a folder-browser detour was tried and rolled back.** Several rounds of UI experiments briefly turned `mazo` into a two-level folder system (a `"/"` in the string meant "lives inside this folder"), then let one card belong to several mazos at once sharing SM-2 progress (a `grupo_id uuid` column, `supabase-flashcards-grupo-id.sql` — the column is still in the DB, harmless and unused now, kept rather than migrated away per this repo's "leave dead artifacts, don't undo a migration" convention), then a "Mover" action to relocate a whole folder or a loose card into an existing one. Direct user feedback across that whole arc was consistently negative — "Estas haciendo un lio tremendo con los mazos carpetas y demas", "no me deja traspasar los mazos enteros... hazlo lo mas sencillo posible hay mucha cosa inutil", and finally the explicit rollback request: "Deja solo mazos y añade las tarjetas que estan dentro solo. Y no se pueden añadir mas mazos dentro. Si yo entro en un mazo, haz mas dinamico lo de añadir, y no me de opcion a añadirlo a otra carpeta, no de opcion a añadirlo en ninguno mas." All of that folder/multi-mazo/move machinery (`arbolCarpetas`, `statsDeCarpeta`, `carpetaNavegando`/`filtroCarpeta`, `FilaCarpetaEditable`, `SelectorMazosMultiple`, the "Mover" flows on both mazos and individual cards) was removed outright — this is the one place in `Flashcards` where dead code was actually deleted rather than left behind, since leaving it would keep reintroducing the confusion that was the whole complaint. The current model: every `mazo` value is one flat entry in a single-level list (a `"/"` in a name, if one somehow exists from the old convention, is just a literal character now, not a separator); `renombrarMazo(viejo, nuevo)`/`eliminarMazo(nombre)` lost their `cascada` parameter (always exact-match on `mazo`); `addFlashcard`/`addFlashcardsBulk` insert into exactly one mazo, no array. `deleteFlashcard`/`eliminarMazo` still do the `grupo_id`-aware orphan cleanup of `flashcards_progreso` (harmless leftover from the multi-mazo detour, and still correct for any card that happens to have `grupo_id !== id` from that brief window) — the only surviving trace of that whole arc.
- **Adding a card is scoped to wherever you are, no destination picker at all.** `NuevaFlashcard`/`ImportarFlashcards` take a `mazoFijo` prop: inside an already-selected mazo, it's set and the card goes straight there — no mazo field is shown, and per the "haz mas dinamico" request the form does *not* close after saving (inputs clear and refocus instead), so several cards can be added back-to-back without reopening anything. Only at the root mazo list (no `mazoFijo`, since there's no "current mazo" to imply) does it ask for a name — that's exclusively how a brand-new mazo gets created; there is deliberately no way to add a single card to more than one mazo. Moving one *after* the fact is a separate thing and does exist: `FlashcardEditableCard` has a **Mover** button next to Editar/Borrar (only when another mazo exists), opening the same plain `<select>` of the other mazos as the whole-mazo send below — it calls `updateFlashcard(id, { mazo })`, which patches only the fields it is handed (`frontal`/`posterior` and/or `mazo`).
- **Etiquetas per card (`flashcards.etiquetas`, a `text[]`).** Added by the user directly in Supabase from a different conversation (`supabase-flashcards-etiquetas.sql` is the repo's record of it, written after the fact; the column is `not null default '{}'` with a GIN index for "contains" filtering). They are deliberately **transversal to the mazo** — the same tag can sit on cards of different mazos — so they answer "repasar todo lo de este tema" without reorganizing anything, which is the thing the folder detour kept failing at. Kept as an array on the row rather than a tags table + join table: few per card, always read with the card, and the GIN index already covers the only query needed. In the UI a card's tags are picked with `SelectorEtiquetas` (shared by `NuevaFlashcard`, `ImportarFlashcards` and `FlashcardEditableCard`'s edit form): every tag you already use anywhere — `todasLasEtiquetas`, computed across all your cards, not just the open mazo — shows as a chip you tap to add, the ones already on the card are chips you tap to remove, and the text field is only for coining a new one (Enter adds it, parsed by the module-level `parsearEtiquetas`, which trims, drops empties and dedupes). Tapping beats retyping here on purpose: free typing was the first version and it invites "porcentajes" and "Porcentajes" living side by side. `ImportarFlashcards` applies one set to the whole pasted block, and `addFlashcard`/`addFlashcardsBulk`/`updateFlashcard` pass the array straight through. In `NuevaFlashcard` the tag selection is the one thing **not** cleared after a save (frontal/posterior are), so you pick "porcentajes" once and add ten cards under it. Reading them: each row in the card list shows its tags as chips (`styles.etiquetaTarjeta`), and above the review panel a "Repasar solo estos temas" chip row ("Todos" + one per tag present in the current scope, `styles.chipEtiqueta`/`chipEtiquetaActiva`) drives `etiquetasActivas` — an array, since the ask was to filter by "las etiquetas que yo quiera": chips accumulate and a card matches if it carries **any** of them (or, not and — requiring all of them at once would land on zero cards almost every time, when the point is reviewing those topics together). It narrows the due count, "Empezar repaso" and the card list alike. `etiquetasDelMazo` only lists tags present in what you are currently looking at, and a `useEffect` drops any active tag that stops existing there (e.g. after switching mazo). This is Flashcards-only — explicitly "SOLO PARA FLASHCARDS, LAS AUTOEVALUACIONES SE DEJAN COMO ESTAN".

### Things to be aware of

- `src/supabaseClient.js` has the Supabase URL and anon key hardcoded inline rather than read from environment variables.
- The Vite config file was originally named `Vite.config.js` (capital `V`), which Vite's default config auto-discovery (lowercase `vite.config.*`) silently ignored — confirmed via `DEBUG=vite:config`, which reported "no config file found" and fell back to zero-config defaults (no `@vitejs/plugin-react`, so no Fast Refresh in `npm run dev`). Renamed to lowercase `vite.config.js`; the react plugin is now actually active.
- `className="animate-spin"` (used on `Loader2` in several places — the root loading screen, `AuthScreen`'s submit button, `GenerarPreguntasIA`'s "Generar" button, and `Duelo`'s "Esperando a un oponente...") never actually spun: there's no Tailwind in this project and no CSS file ever defined an `.animate-spin` keyframe, so the class was applied but inert since the feature was first written (confirmed against the oldest commit of `App.jsx` in the repo — it never worked, this isn't a regression from any later change). Found while investigating a user report that "la animación del duelo al empezar no sale" (turned out to mean this spinner, not the static `Swords` icon nearby, which has never had any animation of its own in any revision of the file). Fixed with a small global `<style>` block in `index.html` (`@keyframes animateSpin` + `.animate-spin { animation: animateSpin 1s linear infinite; }`) rather than per-component, since the class is shared across unrelated components.
- `public/` holds static PWA assets so the app can be "added to home screen": `manifest.webmanifest` (name/short_name "AUTOPIR", `theme_color`/`background_color` `#1C170F` to match the login screen's dark card, `display: "standalone"`) plus `icon-192.png`/`icon-512.png`/`apple-touch-icon.png` — a simple gold "A" monogram (`Big Shoulders Display`, weight 900, on the `#1C170F`/`#E9C878` portada palette) rendered via a one-off Playwright screenshot (no image-generation tool available), not hand-drawn. `index.html` links the manifest, the apple/PNG icons, and a `theme-color` meta. Deliberately no service worker/offline caching — this is just an install/shortcut icon for a small private group, not a full offline-first PWA.
- **Security hardening for sharing with a small group:** `supabase-enable-rls.sql` (one-off, run by the user in the Supabase SQL editor like the other `supabase-*.sql` files) enables Row Level Security on all 10 tables and requires an authenticated Supabase session for virtually every read/write — before this, the client-exposed anon key alone allowed full read/write/delete on every table with no login at all. `preguntas`/`flashcards` writes (insert/update/delete on `preguntas`, update on `flashcards`) are further restricted to the admin's synthesized email (`auth.email() = 'pabloadmin@ruta-pir.local'`), mirroring the existing client-side `isAdmin` gating but now enforced server-side too. `ia_uso` is the one exception left open to the `anon` role: it's only ever touched by `api/generar-preguntas.js`, a serverless function that creates its own Supabase client from the anon key without forwarding the caller's session, so it always acts as `anon`, never `authenticated`. What RLS does **not** cover: no table has a `user_id`/`auth.uid()` column, so rows are all keyed by the free-text `name` field — an authenticated user could in principle read/write another user's `rachas`/`fallos`/`favoritos` row by calling the REST API directly (not through the UI). Fixing that fully needs a schema change (a `user_id` column plus rewritten policies and client queries), judged out of scope for now given the small trusted audience — **since closed** by `supabase-vincular-datos-personales.sql` (run after `supabase-enable-rls.sql`): adds a `user_id uuid references auth.users(id) default auth.uid()` column to `rachas`/`fallos`/`favoritos`/`flashcards_progreso`, backfills it for existing rows by matching `name` against `auth.users.raw_user_meta_data->>'username'` (case-insensitively, with a special-cased `name = 'Pablo'` → username `pabloadmin` since the admin's display name and login username differ), then replaces the earlier `*_auth` policies with `auth.uid() = user_id` checks on insert/update/delete (and on select too for `fallos`/`favoritos`/`flashcards_progreso`, which are purely personal with no shared display) — `rachas` keeps open select since Ranking/Logros show everyone's streaks. No client code changes were needed: `user_id` populates itself via the column `default` on insert, and upserts' `ON CONFLICT DO UPDATE` never touches it after that. Deliberately left out: `duelos`/`duelo_respuestas` (shared state between two named players, doesn't fit a single `user_id` owner column without a larger redesign) and `ranking`/`preguntas`/`flashcards` (already correctly shared/admin-gated, no change needed). `supabase-comprobar-admin.sql` is a read-only check for whether anyone besides the intended admin has registered under (or near) the `pabloadmin` username/email. Enabling RLS required a companion code fix first: the effect that loads `preguntas`/`ranking`/`rachas`/`flashcards` (in the root `AcademiaPIR` component) used to run exactly once on mount, before any login, so under RLS a first-time login/signup in a fresh browser would see those go empty and never recover without a manual refresh; the effect now tracks whether a session existed at that initial load and, if the auth state later transitions from no-session to a session (a fresh login/signup), re-runs the same fetch once now that the client is authenticated. Real signup is still wide open (no invite gate) — anyone who finds the app's URL can self-register and use it fully (short of admin features) via `handleSignup`; there is no code-level fix for this yet, since a real gate needs either disabling public sign-ups in the Supabase Auth dashboard between invites or a server-side invite check, neither of which has been done as of this writing.
